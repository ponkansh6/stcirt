## 背景

現在の `/answer` は検定風の画面で5問を順番に取得して保持するが、画面には1問ずつ表示し、各問の回答を `POST /api/answers` で個別に記録してから次へ進む。利用者は前の問題へ戻れず、5問目まで回答すると完了画面に移る。API は単一の `questionId` と `selectedIndex` を受け取り、単一回答を記録する。

この変更では、1問ごとに画面を切り替える方式をやめ、全5問を一続きのページに縦並びで表示する。受検者はページをスクロールしながら全問に回答し、最終確認後に1回の操作で回答を確定する。既存の検定らしい紙面・マークシートの視覚表現を引き継ぎ、受検票、設問番号、試験要項、回答数、最終確認を通して「ひとまとまりの検定に回答している」ことが伝わる体験にする。

## 現状と前提

- `src/app/answer/use-quiz-session.ts` は問題をカーソル付きで最大5回取得し、5問分をクライアントに保持する。既に全問を先読みする仕組みがあるため、主な変更は回答状態と描画・送信フローである。
- `src/app/answer/quiz-runner.tsx` は現在の問題、5問の進捗、送信状態、完了を描画する。設問見出しへのフォーカス移動は次問表示を前提としている。
- 現在の `POST /api/answers` は `{ questionId, selectedIndex }` 形式で1回答を記録する。リクエストに冪等キーはなく、送信結果の応答が失われて再送すると重複ログになり得る。
- 現行の5問検定では受検中に正誤・解説・点数・合否を示さず、完了画面も回答完了だけを示す。今回の暫定範囲もこの方針を維持する。
- 既存の [18-FIVE_QUESTION_CERTIFICATION_UI_PLAN.md](18-FIVE_QUESTION_CERTIFICATION_UI_PLAN.md) が定めた「1問ずつ確定・次問へ進む」方針は本計画で置き換える。[21-MARKSHEET_QUESTION_UI_PLAN.md](21-MARKSHEET_QUESTION_UI_PLAN.md) の紙面・マークシート意匠は、単問表示に結び付いた記述を除いて本計画へ引き継ぐ。

## 目的と範囲

- 5問すべてを同じページに縦並びで表示し、利用者がスクロールして順に回答できるようにする。
- 選択内容を全問で保持し、各問を行き来して見直し・変更できるようにする。
- 最終確認後、明示的な一括確定操作で5問分を送信する。
- 未回答がある場合は送信を許さず、未回答数と該当設問へ移動する方法を示す。
- 一括送信を原子的かつ冪等に扱えるAPIを追加し、回答が一部だけ記録される状態や再送による重複を防ぐ。
- 仕様書の Requirements / API / Components と実装を同期する。

今回の計画に含めないものは、問題選定順や既存5問の取得方法の変更、ページ再読み込み・離脱後の未確定回答復元、問題編集機能、回答後の個別正誤表示、新しい受検セットの作成である。回答修正は初回に確定した同じ5問の回答セットを更新する。

## 体験と画面仕様

### 試験画面の構成

- 上部に「5問検定」、簡潔な受検案内、全5問であること、回答を最後にまとめて確定することを表示する。実在しない級、所要時間、合格ライン、出題範囲は加えない。
- 5問のカードを一列で縦に並べ、画面上部に受検者名または既存の参加状態を含む控えめな検定ヘッダーを置く。各カードは「第1問 / 全5問」等の明確な番号、問題文、選択肢の順とする。
- 既存の紙面表現を継承し、白系または淡い紙面、濃い本文、控えめな罫線、十分な余白、設問番号の明瞭な階層で整える。マークシートの丸い選択肢表示を維持する。装飾は操作より目立たせない。
- 回答数を「回答済み k/5」と表示し、回答するたびに更新する。必要なら「未回答 n問」も併記し、色だけで状態を表さない。
- ページ末尾に「回答内容を確認してください」等の最終確認領域を置く。5件揃うと一括確定ボタンを有効化し、送信前の最後の操作であると分かる文言にする。初回確定後も修正可能なため、「確定後は変更できません」とは案内せず、修正方法を完了画面に示す。
- 下部固定CTAは必須にしない。採用する場合はモバイルでコンテンツを覆わず、OSキーボード、ブラウザーの表示領域変化、ズーム、フォーカス移動でも設問やCTAが隠れないことを確認する。

### 回答操作

- 各設問は独立した `fieldset` / `legend` と名前が一意な native radio 群で構成し、設問文を読み上げ上のグループ名にする。ラジオ値と既存のシャッフル後・元選択肢 index の対応を崩さない。
- 選択肢は行全体を操作できる明示的な label とし、選択中の丸印・輪郭・状態テキストなど複数の手掛かりを使う。色だけに依存しない。
- 初期状態では全問未回答。回答を選ぶたび、その問だけローカル状態を更新し、APIへ送らない。確定前は何度でも回答変更できる。
- 問題番号の一覧が必要な場合は、各問の回答済み / 未回答を示すページ内アンカーとする。確定済みであるかのように見せず、フォーカスリングと読み上げ名を用意する。別の前問・次問フローは作らない。
- 未回答があるときは一括確定ボタンを無効にし、残り件数と未回答設問番号を表示する。未回答一覧の各項目は該当カードへ移動でき、移動後は設問見出しまたは最初の選択肢へ適切にフォーカスを置く。
- 5件回答済みなら回答数を明示し、全問を見直せる状態で最終確定CTAを使えるようにする。確定前の注意文から確定操作までの視線・読み上げ順を自然にする。
- 一括送信中はすべての選択肢と確定操作をロックし、ボタンを「回答を送信しています…」等へ変更する。再クリックや画面内の重複送信を防止する。
- 初回確定の成功後だけ中立的な完了画面へ進める。完了画面の CTA は「回答を修正する」とし、保存済みの同じ5問と確定済み回答を復元して編集状態へ戻す。修正中の回答はブラウザー内の編集中状態として保持し、修正を明示確定したときに同じ回答セットを一括更新する。修正保存が成功するまでは直前の確定済み回答を保持し、更新失敗時は確定済み状態と編集中の案の両方を失わない。新しい受検や別の回答セットを作る導線は設けない。採点情報は完了画面にも出さない。

### アクセシビリティとレスポンシブ

- 視覚順、DOM順、読み上げ順を一致させる。各 `fieldset` の `legend` に設問番号と設問文を含め、質問同士の境界を明瞭にする。
- 回答済み数、未回答案内、送信状態、送信エラーを適切な `status` / `alert` で伝える。スクロールや設問移動で同じ文言を過剰に読み上げない。
- 選択肢と主要操作は十分なタッチ領域と間隔を持ち、キーボードで全設問・全選択肢・最終CTAに到達できるようにする。フォーカス表示は罫線や選択状態に埋もれない。
- 320 CSS px 相当の狭い幅、長い日本語の問題文・選択肢、拡大表示で横スクロールを発生させず、ラベルと本文を折り返す。5問分の縦長ページで現在位置と送信操作を見失わないよう、回答数や最終CTAへの戻り方を分かりやすくする。
- 未回答導線を使った場合もページ内スクロールで到達先がヘッダー等に隠れず、フォーカス対象が視認できること。sticky 要素があれば同じ条件で検証する。

## 一括提出 API とデータ整合性

### 推奨案

新しい `POST /api/answers/batch` を追加し、5問の回答を1回のリクエストで初回確定し、以降は同じ論理的な回答セットを一括更新する。UIから既存の単問APIを5回連続で呼ぶ方式は、途中失敗で一部回答だけが記録されることと、応答喪失時の再送が重複記録になることを解決しないため、本計画では推奨しない。

リクエスト形の案:

```json
{
  "submissionId": "00000000-0000-4000-8000-000000000001",
  "operationId": "00000000-0000-4000-8000-000000000002",
  "expectedRevision": 0,
  "answers": [
    { "questionId": 101, "selectedIndex": 0 },
    { "questionId": 102, "selectedIndex": 2 },
    { "questionId": 103, "selectedIndex": 1 },
    { "questionId": 104, "selectedIndex": 3 },
    { "questionId": 105, "selectedIndex": 0 }
  ]
}
```

最終契約では `submissionId` と `operationId` は UUID とする。`submissionId` は同じ受検の回答セットを表し、初回確定・修正を通じて維持する。`operationId` は初回確定または各修正保存という1回の書き込み操作を識別し、その通信再試行時には再利用する。`expectedRevision` は初回 `0`、保存後はサーバーが返した現在 revision を指定する。保存先は回答セット、回答、操作記録の専用テーブルとし、既存単問APIのログテーブルを修正履歴として流用しない。

- 既存の参加者 cookie と同一 origin 検証を要求し、参加者 ID はリクエスト body から受け取らず cookie から決める。
- 初回確定時にクライアントが回答セット ID を作成し、その後の修正にも使う。各確定操作で別の operation ID を作成し、その操作の通信リトライでは同じ operation ID と同じ payload を使う。
- サーバーで回答数が厳密に5件であること、重複する `questionId` がないこと、全問が検定用問題であること、`selectedIndex` が各問の選択肢範囲内であることを検証する。新規セット作成時はクライアントの任意の5 IDをそのまま受け入れず、サーバー側で既存の出題定義（現行の先頭5問・順序）と照合する。修正時は提出 ID に保存された同一の5問と照合し、既存回答セットの問題 ID を変更できないようにする。現行に別の受検割当機構があるとは仮定しない。`POST /api/answers/batch` は既存の same-origin 検証と参加者 cookie / session 検証を要求する。rate limit は `POST /api/participants/session` の参加試行にのみ適用され、単問・一括回答 API には現状適用しない（今回新設する要件ではなく、単問 API との互換性を保つ）。
- 初回保存では、全5問の回答と回答セット ID の関連付けを単一DBトランザクションで作成する。修正保存では同じ回答セット内の5回答を単一トランザクションで更新し、失敗時には更新前の確定済み5回答を残す。成功応答は全件保存後に返す。
- 同一参加者・同一 `operationId`・同一内容の再送は既存の成功結果を返し、二重作成・二重更新をしない。同一 operation ID で内容が異なる要求は拒否する。初回確定と意図的な修正は異なる operation ID を使う一方、同じ回答セット ID を維持する。
- 初回確定・修正保存には revision 等の競合検出を設け、古い画面状態からの更新が新しい確定回答を無言で上書きしないようにする。競合時は保存済み回答を再取得し、編集中案を失わずに扱う。
- `GET /api/answers/batch?submissionId=...` は認証済み owner に限り、保存済み revision と5つの選択 index を返す。別参加者の submission は存在有無を区別せず 404 とする。
- 既存の単問 `POST /api/answers` を残す場合、その経路から今回の確定済み回答セットを追加・変更できるか確認し、一括APIとの整合性を守る。参加者セッション全体を一回の受検とみなして回答修正を拒まない。
- 回答ログの現在の意味と利用箇所を調べ、同じ回答セットの修正でログ行を追加するのではなく、論理的なセットを更新できる保存モデルにする。必要なら回答セット／操作の識別情報や提出記録を持つテーブル・一意キーを追加する。schema 変更を行う場合は migration と本番スキーマドリフト検出要件に従う。
- 既存の `POST /api/answers` は他の利用箇所との互換性を保つ。新フローは一括APIを使用し、既存契約を無断で配列形式へ変更しない。
- レスポンスと画面に正誤・正解・解説は含めない。記録成功の確認、回答セット ID と新しい revision を返し、完了画面から修正を始めるときは保存済み回答を復元できるようにする。
