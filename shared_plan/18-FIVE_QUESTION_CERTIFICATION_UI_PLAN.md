# 全5問の検定風 UI

> **承認済みの後続変更:** 当初この計画は UI のみの変更として既存 `questions` / `answer_logs` を使う前提だったが、2026-10-04 のユーザー指示により専用の `exam_questions` / `exam_answer_logs` を作成し、この検定アプリはそのデータだけを読む・記録する構成へ変更する。既存の学習データと回答履歴は保持し、初期 migration で固定 ID / key を持つ日本語 IT リテラシーのサンプル問題5問を冪等に追加する。採点・合格基準・検定成績 UI は引き続き追加しない。

## Context

現在の回答画面は、問題を順番に取得して回答を記録するクイズ UI である。問題は `questions.id ASC` の順に `/api/questions/next?afterId=` から取得し、回答は既存 API に問題ごとに送信される。回答後のレスポンスには正誤と解説が含まれ、画面には正答数・正答率・進捗と正誤・解説が表示される。ホームには全体統計と回答画面への CTA がある。

今回の改稿は UI 計画の具体化であり、以下の既定フローを変更しない。この変更では既存の回答フローを「全5問の検定」として見せる。**採点・合格判定は設けず、UI の作り替えだけを行う。** 開始時に既存 API から ID 昇順で先頭5件を順次取得してクライアントに保持し、その実行中の出題セットを固定する。回答ログはこれまでどおり問題ごとに記録する。回答送信を再試行した場合は追加の回答ログが記録される可能性がある。画面では回答 API の正誤・解説フィールドを使わず、5問目の回答成功後に成績のない完了画面を出す。

今回の設計対象は検定らしさを伝える視覚階層、ホーム・受検中・完了のレイアウト、コピー、レスポンシブ表示、状態表示、アクセシビリティと UI 受け入れ条件である。全5問の事前取得、出題順、回答確定・記録、エラー処理、再開始など、後述の仕組みは既定仕様として維持する。

## 確定した設計判断

| 項目                      | 選択                                                                                    | 理由                                                                   |
| ------------------------- | --------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 出題数                    | 1回につき5問                                                                            | 検定として固定長の体験にする                                           |
| 問題の選び方              | 開始時に既存 API で `questions.id ASC` の先頭5件を順次取得し、クライアントに保持        | 出題セットを実行中に固定でき、API・DB 変更も不要                       |
| 開始時                    | まず5件の取得を完了し、その後1問目を表示                                                | 初回は `afterId` なし、その後は直前 ID を使って5件まで取得する         |
| 直接 `/answer` にアクセス | 5件の取得後に1問目を開始。取得数不足・初回404なら開始不可画面を表示                     | ホームを経由しない場合も同じ5問条件を保証する                          |
| 回答確定                  | 選択後に確認操作を挟み、送信中と確定後は二重送信できないようにする                      | 検定らしい回答確定の手順を作り、誤操作を減らす                         |
| 送信成功後の進行失敗      | 成功した回答を先に確定状態として保持し、再試行は進行・取得だけにする                    | 回答ログを重複して作らない                                             |
| 問題が回答前に消えた場合  | 既存回答 API が失敗したことを表示し、現在の回答と設問を保持して終了・再読込の案内を出す | 削除済み問題への回答は記録できないため、出題セットを勝手に差し替えない |
| 回答後の表示              | 正誤・解説・点数・正答率・合否を表示しない                                              | 要望は UI 変更のみで、採点を扱わない                                   |
| 完了                      | 5問目の回答記録が成功した後に、成績なしの完了画面を表示                                 | 既存の回答記録を保ち、検定の終了を明示する                             |
| 問題が5件未満             | ホームの問題数で事前に開始を抑止し、検定開始時の取得でも確認                            | 件数表示と実際の取得結果の不一致も扱う                                 |
| 実行状態                  | UI state のみ。リロードや再マウント時には先頭から                                       | セッション永続化は今回の UI-only 範囲外                                |
| 再開始                    | 出題カーソル、保持した5問、回答状態、進捗、送信・取得中状態、エラーをすべて初期化       | 新しい実行として先頭から始める                                         |

この方式では毎回同じ先頭5問になる。問題のランダム化・出題履歴を使った重複回避は今回含めない。

## UI 仕様

### ホーム / 検定の案内

- 検定の案内と開始 CTA をホームの主役にし、既存の全体統計は視覚的に二次情報として残す。全体統計は検定1回ごとの成績ではないと分かるラベルや配置にし、今回の検定の点数・合否と誤認させない。取得 API、回答ログ、統計データは変更しない。
- ページ上部に小さなサービス名または既存プロダクト名、主見出し「5問検定」、短い説明を置く。続く案内カードを検定の表紙・ブリーフィングとして構成し、「全5問」「順番に出題」「回答を記録します」を短い要項として読めるようにする。実在しない試験名称、級、分野、所要時間、受検資格、合格ラインは加えない。
- カード内は見出し・要項・主 CTA の順に情報を整理し、主 CTA は「検定を開始する」とする。CTA の近くに開始可否が分かる問題数の状態を置き、キーボードフォーカス、押下、無効状態を明瞭にする。
- 全体統計は案内カードより下または視覚的に軽い領域へ置き、見出しを「これまでの回答状況」など全体集計と分かる名称にする。単位が既存データから確認できない場合は、数値の単位を新たに推測して表示しない。
- 問題数が5件未満なら CTA を開始不可にし、「問題が5問そろうと開始できます」など不足が明確な案内を表示する。表示件数にかかわらず、`/answer` 直アクセス時も開始に先立って API で5件の取得を試みる。
- `/answer` への直接アクセス時は、開始前の取得状態を表示する。取得により5問そろえば1問目へ進み、初回404または5問未満なら検定を開始せず、ホームへ戻る導線と不足の説明を表示する。取得中・通信失敗は不足扱いにせず、再試行可能なエラーとして表示する。
- 得点・合格基準の存在を示唆する文言や装飾は使わない。

### 視覚デザインと情報階層

- 公的な検定案内を思わせる落ち着いた「試験要項・受検票」の雰囲気を、色・罫線・余白・文字組で作る。深いインク色を主色、金色を小さな番号・区切り・アイコンなどのアクセントに使い、白または温かみのある淡色の面で本文を支える。金色の小さい文字を本文や状態ラベルに使わず、コントラストを実測してから色を確定する。
- 画面は中央に読みやすい幅のコンテンツ領域を持ち、カード境界は細い罫線と控えめな角丸で表現する。二重線や隅の小さな装飾は表紙のアクセントに限り、設問・選択肢周辺を飾りすぎない。大きな余白と明確な見出し階層で、最初に読む情報と次の操作をすぐ見つけられるようにする。
- 書体は見出しに存在するフォントのセリフ系または明瞭な太字、設問・選択肢・操作には可読性の高いサンセリフ系を使う。新しいフォント依存は追加しない。日本語の文字サイズ、行間、句読点の折返しを優先し、設問本文は本文より一段大きく読みやすくする。
- 検定らしさは文言と要項、設問番号、整った罫線・余白・状態表示で示す。金の紋章、合格印、証書風の完成演出など合格・認定を連想させる表現は使わない。
- 色は役割（通常、選択中、送信中、エラー、完了）を補助するものとして使い、状態は文言・アイコン・形でも識別できるようにする。色値は候補に留め、実装時に背景とのコントラストを測定する。

### 受検中・完了の具体的な画面構成

- 受検画面の上部にプロダクト名と「5問検定」を控えめに示す。メイン領域では設問番号を最も強い視覚要素にし、「第1問」のように表示する。直下に設問本文、選択肢、選択を見直せることが分かる補助文、主操作「回答を確定する」の順で配置する。
- 現在の設問位置と、回答がサーバに記録済みの数は別の情報として表示する。設問位置は `第 n 問 / 全5問`、記録状態は回答成功後に `回答記録済み k/5` とする。現在問 n を回答済み数 k として表示しない。5つのステップ表示では各問を「回答済み」「現在」「未到達」のいずれかで表現し、現在位置と記録済み数を誤認させない。
- 設問領域の進捗は細い5区分のステップ列または同等の軽いインジケーターとし、画面幅が狭い場合も各区分を見分けられる。`progressbar` を使う場合は何を表す進捗かを名前で明記する。現在の設問位置を表す値ならその値を、回答記録を表す値ならサーバ成功後の記録数を示し、両者を1つの進捗値に混ぜない。
- 選択肢は各行またはカード全体が選択操作となる十分な領域を持つ。未選択・選択中・送信中を枠線、背景、チェック記号、テキストラベル等で区別し、選択中は「選択中」が視覚的にも明確であること。選択肢の記号は選択肢ラベルとして既存の回答値と混同させずに見せる。
- 確定前は選択肢の変更が可能であることを示し、確定後は回答操作をロックする。送信中はボタン文言を「回答を記録しています…」にし、操作不能であることも伝える。記録失敗時は選択と設問を維持し、「回答を記録できませんでした。通信状態を確認して、もう一度お試しください。」と再試行を案内する。APIやDBの詳細、正誤を示唆する表現は出さない。
- 完了画面では見出し「回答完了」、本文「全5問の回答を記録しました。」を使う。これは受検操作の終了を意味し、合格・認定を表さない。証書、受検ID、点数、評価の枠、合格を思わせる印章や紙吹雪は表示しない。主 CTA は「もう一度受検する」とし、既存の再開始動作に結び付ける。
- 初期取得、開始不可、通信エラー、回答送信中、記録成功、記録失敗、完了の各状態は、同じレイアウト内の一貫したステータス領域で表す。エラーは通常本文から離しすぎず、内容と次の操作を一緒に示す。エラーや不足で主操作を使えない場合は理由を隣接表示し、無効化だけで終わらせない。

### レスポンシブと操作性

- デスクトップでは本文の行長を抑えた中央カラムとし、ホームの要項・CTA を統計情報より上に置く。タブレットではカラムを広げすぎず、余白を段階的に縮める。
- モバイルでは設問文と選択肢を最優先する単一カラムにし、設問本文を狭い画面でも十分な文字サイズと行間で表示する。各選択肢は縦に並べ、長い日本語の改行でラベルや選択状態が押し出されないようにする。水平スクロールを発生させない。
- 回答 CTA は選択肢の後に置く。画面下部に追従させる場合は高さを抑え、フォーカス中の入力・ボタン・設問見出しを覆わない。ソフトウェアキーボード表示時、拡大表示時、フォーカス移動時にも対象が隠れずスクロール可能であること。原則として sticky を必須にしない。
- タッチ操作領域は十分な大きさと間隔を取り、見た目の余白だけで操作範囲を狭めない。ページ上の情報順と読み上げ順を一致させる。

### 出題画面

- 検定中であることが分かる簡潔な試験用フレームにする。
- ヘッダーに `第 n 問 / 全5問` を表示し、5問のステップ状態を示す。現在問の番号は出題位置であり、回答記録済み数とは別に扱う。視覚的な進捗には適切なアクセシブル名、値、最大値を付ける。
- 問題文と選択肢を読みやすく配置し、選択肢の選択状態を視覚・アクセシビリティ属性の両方で示す。
- 選択後は「回答を確定する」操作を提示する。確定前に選択を見直せることが明確であること。
- 検定開始時に既存の `/api/questions/next?afterId=` を使用し、最初は `afterId` なし、その後は直前の問題 ID を渡して5件を順次取得する。5件すべてを得るまで設問を出さず、ID と問題データを UI state に保持して実行中のセットを固定する。初回404または5件未満なら開始不可状態にする。途中の取得失敗なら取得済みデータを保持し、不足分の取得だけ再試行する。
- 確定操作後は既存回答 API に送信し、送信中は操作を無効化する。POST が成功したらその回答をただちに成功済みとして保持し、成功済み回答はロックする。
- API が返す正誤・解説は UI で参照せず、正解表示、解説、得点、正答率、合否を出さない。
- 1〜4問目の回答が記録されたら保持済みの次の問題へ進む。進捗と設問番号を更新する。POST 成功後に進行処理または通信で失敗した場合は、成功済み回答を保持し、回答 POST を再送せず、進行・必要な取得処理だけを再試行する。通常の5問セットは開始時にキャッシュ済みなので、進行時にネットワーク再取得を要しない。
- 5問目の回答が記録されたら次の問題を要求せず、完了画面へ移行する。
- 回答 POST が失敗した場合、回答と設問を保持し、同じ回答を再試行できるようにする。サーバ側では記録済みだが応答だけ失われたケースなど、POST 再試行によって同じ問題の回答ログが追加で記録される可能性を UI-only では排除できないことを明記する。失敗を正答・誤答として見せない。
- 開始時に取得済みの問題が DB 変更等で回答 API に拒否された場合、現在の回答を保持してその問題に留まり、回答を記録できなかった旨とホームへ戻る導線を表示する。取得セットの別問題への差し替えや自動スキップはしない。

### 完了画面

- 「回答完了」と全5問の回答記録が終わったことを示す。
- 得点、正答数、正答率、合格・不合格、正答や解説は表示しない。
- 新しい実行を開始する導線を置く。押下時には出題カーソル、保持した問題セット、選択・回答状態、進捗、送信・取得中状態、エラーをすべて初期化し、先頭5件を再取得して最初の問題から開始する。
- 完了後に回答履歴・セッションを復元する機能は作らない。

## 候補ファイル

実装開始時に現行ファイル名を確認し、責務が一致する範囲だけ編集する。

- `src/app/page.tsx` またはホームのクライアントコンポーネント: 検定案内・開始 CTA を主表示にし、既存の全体統計を二次情報として維持。
- `src/app/answer/page.tsx` と回答クライアントコンポーネント: 直接アクセス時の初期取得・不足表示、5問の事前取得と保持、進行、回答確定、完了画面を実装。
- 既存の回答用コンポーネントが分かれている場合は、選択肢・問題表示のスタイルとアクセシビリティを必要な分だけ更新。
- `openspec/specs/stcirt/spec.md`: UI 要件と、既存 API・回答記録を維持することを反映。

新しい API、DB 列、テーブル、依存パッケージ、環境変数は追加しない。

## 実装フェーズ

1. **案内画面** — 検定の表紙・ブリーフィングと開始可能条件を用意し、全体統計は検定単位の成績ではないことが伝わる二次表示として残す。
2. **5問の固定セット** — 既存の順次取得を開始時に5回まで呼び、取得した問題を UI state に保持する。ホームと `/answer` 直アクセスの両方で5件未満・404・通信失敗を適切に表示する。
3. **回答確認・ロック** — 選択、確定、送信中、送信成功、進行エラーの状態を分ける。POST 成功後は状態を先に確定し、進行再試行で再 POST しない。既存回答 API と回答ログを保ちつつ、レスポンスの正誤・解説を表示に使わない。
4. **完了・再開始** — 5問目の送信成功後の完了画面と、最初から再開始する導線を追加する。
5. **仕様同期と確認** — `openspec/specs/stcirt/spec.md` を更新し、後述の将来テストケースに沿って UI の状態遷移とアクセシビリティを確認する。

## アクセシビリティとレスポンシブ

- 設問番号を見出しとして構造化し、問題文と選択肢の関連がスクリーンリーダーにも伝わるようにする。
- 選択肢はキーボード操作可能にし、選択中・無効・送信中を色だけで区別しない。
- 設問位置と回答記録数はそれぞれテキストでも伝える。支援技術にも進捗の意味を区別した名前、現在値と最大値を伝える。
- 確定後・設問移動後は新しい設問見出しまたは状態メッセージへ適切にフォーカスを移す。送信失敗は `aria-live` 等で通知する。
- モバイル幅でも問題文・選択肢・確定ボタンを読みやすく縦に配置し、横スクロールを発生させない。タップ領域を十分に確保する。
- 動きのある遷移を加える場合は `prefers-reduced-motion` を尊重する。
- 文字色と背景色は通常テキストで WCAG 2.2 AA のコントラスト比 4.5:1 以上、大きな文字は 3:1 以上を満たす。操作部品や状態を識別する境界・アイコン等も非テキストコントラスト 3:1 以上を目安に測定する。淡い金の罫線を必須操作の境界に使わない。
- 200% 拡大や狭いビューポートで内容の欠落・二方向スクロールを起こさない。フォーカスインジケーターを常に視認できるようにする。
- 色だけで回答済み・現在・未到達、選択、エラーを伝えない。エラー文には次の行動を含め、通信エラーと開始不可を別状態として表す。

### UI 受け入れ基準

1. ホームの第一画面で「5問検定」、3つの要項（全5問・順番に出題・回答記録）と「検定を開始する」が視線順に把握でき、全体統計は検定1回の成績と誤認されない。
2. 問題不足・取得中・通信失敗はそれぞれ異なる説明と次の操作を持ち、開始不可の理由が無効ボタンだけに依存しない。
3. 受検中は設問番号、設問本文、全選択肢、選択操作、確定 CTA が明確な順序で並び、設問番号が画面内の強い見出しとして認識できる。
4. 現在の設問位置 `第 n 問 / 全5問` と、回答成功後の `回答記録済み k/5` を別に表示する。5ステップの状態も回答済み・現在・未到達が視覚とアクセシビリティ情報で区別され、選択だけの未送信回答を回答済みに数えない。
5. 未選択、選択中、送信中、送信失敗、記録成功の各状態を文言と形状等で判別でき、色だけに依存しない。送信失敗時は設問と選択を保ち、再試行方法を示す。
6. 完了見出しが「回答完了」であり、本文は5問の回答記録を伝える。合格・不合格・認定と混同する点数、証書、ID、演出は表示しない。
7. モバイル表示では長い日本語の設問・選択肢が主役で、折返し、操作領域、スクロール、拡大表示に問題がなく、sticky UI がフォーカス対象を覆わない。
8. キーボードのみで全選択肢、確定、再試行、再開始を操作でき、フォーカス表示・順序・設問移動後のフォーカス・ライブ通知を確認できる。
9. 通常文字、大きな文字、操作部品、状態アイコンのコントラストを測定して基準を満たす。未測定の金色アクセントを本文や必須操作の識別に使わない。
10. reduced-motion 設定で不要な動きを止めても、状態変化と操作結果を理解できる。

## 非目標

- 採点、正答数・正答率の表示、合格基準、合否判定。
- 回答後の正誤・解説表示。
- 出題 API、回答 API、DB スキーマ、既存問題データ、回答ログ形式の変更。
- 問題のランダム化、毎回異なる問題選定、出題履歴による重複回避。
- 実行途中の再開、セッション永続化、ユーザー単位の検定結果保存。
- 環境変数、依存関係、LLM、作問機能の変更。
- 集計・統計 API や回答ログの削除。全体統計はホームに二次情報として残し、検定ごとの成績とは区別する。

## 受け入れ条件

1. ホームに検定の概要と主 CTA があり、全体統計は二次情報として残り、今回の検定の成績・合否と混同されない。
2. 問題が5件未満では開始できず、不足理由が利用者に分かる。
3. 開始時に既存 API で ID 昇順の先頭5件を取得・保持し、`第1問` から `第5問` まで同じセットが順に表示される。
4. 現在の設問位置が第1問から第5問まで正しく更新され、回答記録済み数は各 POST 成功後にだけ増える。2つの値は別々に伝わる。
5. 回答は選択後の確定操作で既存 API に送信され、記録される。連打しても二重送信されない。
6. UI に正誤、解説、得点、正答率、合否が表示されない。
7. 5問目の回答送信成功後に、成績なしの完了画面が表示される。
8. `/answer` 直アクセスでも5問を事前取得し、初回404・5件未満・通信失敗は開始前の案内または再試行として表示される。
9. POST 成功後に進行・取得で失敗しても成功済み回答を保持し、進行だけを再試行して POST を再送しない。
10. 回答 POST 自体が失敗した場合は回答を保持して再試行できる。POST 再試行では回答ログが追加記録されうる。
11. 回答対象の問題が DB 変更等で拒否された場合、回答を保持してその設問に留まり、差し替え・自動スキップしない。
12. 再開始でカーソル、回答、進捗、保留中・エラー状態をリセットして先頭5件を再取得する。
13. 既存 API、DB、回答ログ形式、環境変数、依存関係に変更がない。

## 将来のテストケース（説明のみ）

- ホームで検定案内が主表示、全体統計が二次表示となり、統計が検定単位の成績と混同されない。問題数4件以下では開始不可の説明が出る。
- `/answer` 直アクセス時にも `afterId` なしから既存 API を呼び、以後 `afterId` を使って ID 昇順の先頭5件を開始時にすべて取得して保持する。
- 初回404・取得結果が5件未満では開始せず案内し、取得通信エラーでは取得済みデータを保持して不足分だけ再試行できる。
- 各設問で設問番号・ステップ状態が更新され、回答記録済み数は POST 成功後に更新される。開始時に保持した同じ5件が使われる。5問目の回答成功後は次の取得 API を呼ばず「回答完了」を表示する。
- 未選択では確定できず、選択後に確定できる。送信中の二重操作は無効化される。
- API レスポンスに正誤・解説を含めても、画面にそれらや得点・合否が出ない。
- 回答 POST 失敗後に選択内容を保持し、再送信できる。再送信により回答ログが追加で記録される可能性を許容する。
- POST 成功後に進行・次問表示が失敗した状態から、POST を再送せず進行だけを再試行する。
- 回答対象が DB 変更等で拒否された場合に選択内容を保持し、問題を差し替えず設問に留まる。
- 再開始でカーソル、保持データ、回答、進捗、保留中・エラー状態をリセットし、最初の5件を再取得する。画面再マウントでは開始前状態から先頭へ進む。
- キーボードだけで選択・確定・再開始でき、設問移動後のフォーカスとライブ通知が適切である。
- 狭い画面と reduced-motion 設定でレイアウト・操作性が保たれる。
