# 催し共通PINと参加者名による回答記録

## 目的

ホームから回答開始までをわかりやすく、迷いや緊張が少ない導線に整える。参加者は名前と、主催者から案内された催し共通の4桁PINを一度入力して参加する。有効な参加者Cookieが残っていれば再入力を省略できる。以降の回答は参加者名に紐づけて記録する。

ホームの「これまでの回答状況」セクションと統計カードは削除する。これは統計UIの削除であり、既存の回答ログや集計用データを削除する意味ではない。現在の回答APIは匿名でも回答をDBに記録しているため、過去のログは保持し、新しい回答のみ参加者IDを付与する。

## 現状

- `src/app/page.tsx` のホームに問題数・本日の解答数・本日の正答率を示す「これまでの回答状況」がある。数値は `src/lib/db/repository/answer-repository.ts#getStats()` による集計で、`tests/e2e/home.spec.ts` が見出しを確認している。
- 現在の回答フローは `src/app/answer/page.tsx` → `quiz-runner.tsx` → `use-quiz-session.ts` → API client `src/lib/api/client.ts` → `POST /api/answers`。回答は正解判定後に `recordAnswer` 経由で `exam_answer_logs` に記録される。
- 現在の回答ログは questionId、selectedIndex、isCorrect、answeredAt を保持し、回答者を識別する情報はない。回答 API の `submitAnswerSchema` にも名前やPINはない。
- 回答中の状態はReact stateで管理され、リロード時に再開されない。調査した `src` / `tests` / spec の範囲では localStorage / sessionStorage を使った回答保存は見つかっていない。実装時に対象範囲を再検索し、もし要件上削除すべきブラウザー保存が見つかれば併せて取り除く。
- `openspec/specs/stcirt/spec.md` には匿名回答送信（R2）とホームの回答状況（R4）の要件があるため、新しい回答者識別フローと統計表示の削除に合わせて更新する。

## 設計方針

| 論点             | 方針                                                                                                                                                                                                                                        | 実装時に確認すること                                                                                                                                                    |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 参加者           | `exam_participants`（または既存命名規則に沿うテーブル）にID、trim+Unicode NFC正規化名、表示名、作成日時のみを保存する。PIN関連の列は持たない                                                                                                | 現行スキーマ・migrationの命名と既存DB制約に合わせる                                                                                                                     |
| 名前             | 前後空白を除去してUnicode NFCに正規化した値を検索キーとして扱う。空文字は拒否する。大小文字は区別し、NFKC変換・内部空白の圧縮はしない                                                                                                       | 表示名はtrim後の入力を保持する。NFCと大小文字区別をテストで固定する                                                                                                     |
| 同名             | 同じ正規化名は同一参加者として再利用する。別人の同名者を識別したり、同名者同士を分離したりする要件は設けない。一意制約は同時登録時に重複レコードを作らないための内部制約として使う                                                          | 競合登録時に一方の作成結果を再取得して利用する                                                                                                                          |
| 催し共通PIN      | 4桁PINは主催者が事前に設定して参加者へ案内する。参加者がPINを作成・登録・変更する画面や機能は作らない。参加者ごとのPIN、再発行、同名者のPIN衝突UXも設けない                                                                                 | サーバー設定の方法と催しごとの配布手順を運用手順に明記する。主催者向け管理UIは新設しない                                                                                |
| PIN設定の保護    | サーバー設定にはPIN平文を置かず、ランダムsalt付きKDFハッシュを秘密の環境設定として注入する。設定値、入力PIN、ハッシュをログ・エラー・分析イベントへ出さない。PIN設定が欠けている・壊れている場合は参加セッションを発行せずfail closedにする | KDF方式・パラメーター、saltとハッシュ値の形式、設定方法、ローテーション手順を実装に合わせて文書化する。PINは4桁で候補が10,000通りしかないため、強い本人確認には使わない |
| 試行制限         | 正規化名単位で失敗試行を制限する。既定値は5回/15分とし、送信元によらず状態を全アプリインスタンスで共有するDB等に保持する。単一プロセス内メモリには置かない                                                                                  | PIN試行制限は名前単位とする。共有ストアが用意できない場合は公開前の阻害事項とする                                                                                       |
| 参加者セッション | 名前+催し共通PINを受けるセッションAPIが参加者を検索または作成し、署名済みHttpOnly/SameSite=Lax cookieを発行する。PINは一致後に破棄し、セッションや回答POSTに含めない                                                                        | 署名鍵、PIN設定ハッシュ、セッション期限の設定方法と未設定時の失敗動作を定める。本番ではSecure属性を付ける                                                               |
| Cookie再利用     | Cookieがあるだけでは認証済みとしない。照会APIと各保護APIで署名、participant ID、有効期限、DB上の参加者存在、催し設定versionを検証する。有効Cookieが残っている場合は名前とPINの再入力を省略する                                              | Cookie期限は既定30日を例とし、催し期間に合わせて設定可能にする。PIN変更時は設定versionを更新し、それ以前のCookieを無効化する                                            |
| 回答API          | `POST /api/answers` は有効な参加者Cookieを必須とし、cookie検証済みparticipant IDのみを回答ログに記録する。匿名POSTや本文指定participant IDを受け付けない                                                                                    | Cookie送信時のCSRF対策としてSameSite=Laxに加えてOriginまたはCSRF検証を行い、既存クライアント/E2EもCookie前提に更新する                                                  |
| 既存回答ログ     | `exam_answer_logs.participantId` をnullableで追加し、既存匿名ログはNULLのまま残す。新フロー後の回答のみ参加者IDを設定する                                                                                                                   | 過去回答を名前に推測で割り当てない。統計表示を削除しても、既存ログ・集計機能・データは削除しない                                                                        |
| ブラウザー保存   | PINやCookie値をlocalStorage/sessionStorageに保存しない。Cookieはブラウザー管理のHttpOnly属性で扱い、画面stateにもPINを送信後に残さない                                                                                                      | 現状はlocalStorage保存が見つかっていないため、実装時再検索で確認する                                                                                                    |

## 画面と操作

- 初回の参加画面は名前とPINを一つのフォームにまとめ、主ボタンは「はじめる」とする。参加者登録かログインかを選ばせず、PINを作成する操作も出さない。
- 入力欄の前に短い案内を置く。例：「全5問です」「回答はお名前と一緒に記録されます」「主催者から案内された4桁PINを入力してください」。計測していない所要時間は表示しない。
- ホームと回答画面で同じ説明を繰り返さない。ホームでは回答へ進む主CTAを明確にし、回答画面では必要な入力案内だけを示す。統計削除後も、ホームから回答開始へ自然につながる導線を残す。
- 認証照会中は入力フォームを一瞬表示せず、短く安定した読み込み表示にする。照会失敗や期限切れCookieは初回入力画面へ移る。
- Cookieで認証済みの場合は「○○さん」と「検定をはじめる」を表示する。控えめな「別の名前で参加」導線も用意する。Cookieだけで問題を自動開始しない。
- 「別の名前で参加」ではサーバー側でCookieを削除し、クイズの進行stateをリセットしてから初回入力画面へ戻す。
- PINは単一入力欄とし、`inputMode="numeric"`、先頭0保持、貼り付けを可能にする。送信後はPINをstate・入力欄から消去する。PIN欄の意味と桁数をアクセシブルにし、入力エラーを該当欄に関連付ける。
- PIN不一致、未設定、試行制限などの失敗は簡潔で具体的な案内にする。名前はエラー後も保持し、PINは再入力できるよう空にする。存在しない参加者名を列挙する応答にしない。開始画面に過度な不安をあおる警告を置かない。
- 回答途中にCookieが期限切れまたは無効になった場合は、選択中の回答を画面内に維持して再ログイン導線を示す。再ログイン後に回答を自動送信したり、回答途中を永続再開したりする機能は追加しない。

## 実装手順

1. **実装前の確認**
   - 作業ディレクトリから解決される `node_modules/next/dist/docs/` の関連ガイドを読み、現行Next.jsのルールに従う。
   - `src` / `tests` / specを再検索し、認証状態・回答内容がブラウザー永続領域に保存されていないか確認する。
   - 現行DB、migration、環境設定、共有レート制限ストア、回答API、画面構造を確認する。

2. **データモデルとmigration**
   - 参加者テーブルを追加する。保存する列はID、trim+NFC正規化名、表示名、作成日時のみとし、正規化名に一意制約を置いて同時作成による重複だけを防ぐ。
   - `exam_answer_logs` にnullableのparticipantId外部参照を追加する。既存レコードはNULLのまま維持し、migrationで削除・再割当しない。
   - SQLite/Tursoでの外部キー、index、migration適用順を既存Drizzle構成に合わせる。生成migrationに既存ログの破壊的操作がないことを確認する。
   - テストDBヘルパー `tests/helpers/db.ts` が新スキーマを初期化できるよう更新する。

3. **参加者リポジトリと催し共通PIN検証**
   - 参加者の検索・作成を `src/lib/db/repository/` の既存パターンに沿って実装する。同じ正規化名は同じレコードを返し、競合登録時も一意制約を利用して既存レコードを返す。
   - 正規化名は前後空白を除去した後にUnicode NFCへ変換する。大小文字は区別し、NFKC変換と内部空白の圧縮は行わない。
   - 参加者が入力した4桁数字文字列をサーバー設定済みの催し共通PINハッシュと照合する。先頭0を含む文字列として扱う。参加者レコードにPINハッシュを作らない。
   - 主催者が秘密の環境設定として用意するKDFハッシュの生成方法、salt・パラメーター形式、環境ごとの設定手順、変更時の設定version更新を記す。平文PINをソース、設定例、ログ、エラーに書かない。PIN未設定や不正設定の場合は認証を成立させない。
   - 正規化名単位の既定5回/15分の失敗制限を共有ストアで実装する。送信元情報に依存せず、制限時の再試行可能時刻をわかりやすく示す。

4. **参加者セッションAPIとCookie照会**
   - 名前+共通PINを受ける開始APIを用意する。成功時に参加者ID、期限、設定versionを含む署名済みセッションCookieを発行する。PINはレスポンス・Cookie・回答POSTに含めない。
   - CookieはHttpOnly、SameSite=Lax、適切なPath、期限を設定し、本番ではSecureを付ける。期限は既定30日を例として催し期間に合わせ設定可能にする。
   - Cookie照会APIを設け、クライアントが画面表示を決める前に認証状態を得られるようにする。照会および保護APIは署名、participant ID、期限、DB上の有効参加者、現在の設定versionを検証する。Cookieがあるだけで認証済みにしない。
   - PIN変更時は設定versionを更新し、それ以前の全Cookieを無効化する。失効Cookieは通常の初回画面へ戻し、別参加導線ではサーバーでCookieを削除する。
   - 設定・署名鍵不足や不正時はfail closedにする。PIN、ハッシュ、秘密値、Cookie値、署名トークンを入力ログ、例外ログ、トレースへ含めない。

5. **回答APIとCSRF**
   - `POST /api/answers` は有効Cookieを必須にし、Cookieから検証したparticipant IDだけを回答ログに紐づける。本文のparticipantIdを使わず、新しい匿名POSTも受け付けない。
   - SameSite=Laxに加えてOriginまたはCSRFトークン検証を行う。既存API client、画面、テストをCookie利用に揃える。
   - 既存の匿名ログはDBに保持し、participantId=NULLのままにする。新しい回答だけに参加者IDを設定する。

6. **回答開始画面と再認証UX**
   - `src/app/answer/page.tsx`、`quiz-runner.tsx` および関連state/API clientに、起動時のCookie照会、初回の名前+PINフォーム、認証済みの開始画面を実装する。
   - Cookie照会中は落ち着いた読み込み表示を保ち、未確認の状態で入力フォームをちらつかせない。認証済み画面では「○○さん」「検定をはじめる」「別の名前で参加」を示し、クイズは明示的な操作後に始める。
   - 初回フォームは短い説明と一つの「はじめる」ボタンに絞る。入力・エラー・送信中・制限状態をアクセシブルに伝え、失敗時は名前を保持、PINを消去する。
   - PIN欄は数字入力を促すが、先頭0と貼り付けを維持する。送信後にPINを消去し、ブラウザー永続領域へ保存しない。
   - 別参加操作はサーバーCookie削除とクイズstateのリセット後に初回画面へ戻す。回答中にCookieが無効になった場合は画面内の選択を保ち、再ログインを促す。再ログイン後の自動送信・永続再開は追加しない。
   - 既存の設問取得、採点、解説、5問完了フローは維持する。

7. **ホーム統計の削除**
   - `src/app/page.tsx` から「これまでの回答状況」見出しと問題数・本日の解答数・本日の正答率カードを取り除く。
   - ホームから回答開始への主CTAがわかりやすいことを確認する。ホームと回答画面に同じ案内を重複して出さない。
   - ホーム専用の統計取得が不要になる場合は呼び出しを除く。`getStats()` に他の利用箇所がないことを確かめてから削除可否を判断し、回答ログや不要と確認できないDB機能を削除しない。

8. **仕様書・テスト・運用手順**
   - 実装変更と並行して `openspec/specs/stcirt/spec.md` のRequirements/API/Data Modelを更新する。R2は参加者Cookie必須の回答、R4は統計のないホームと回答開始導線に同期し、旧匿名ログをNULLのまま保持する方針を明記する。
   - API、参加者列、共通PIN設定、セッション設定version、Cookie属性と照会、エラー、名前正規化、レート制限、CSRF、期限切れ時の操作を仕様書と実装で一致させる。
   - 既存specの要件参照に合わせて関連単体/API/E2Eテストを更新する。主な対象は `tests/api/answers.test.ts`、`tests/db/answer-repository.test.ts`、`tests/answer/use-quiz-session.test.tsx`、`tests/answer/quiz-runner.test.tsx`、`tests/answer/page.test.tsx`、`tests/api/client.test.ts`、`tests/e2e/answer.spec.ts`、`tests/e2e/home.spec.ts`。
   - 参加者API/repositoryは新規名、同名再利用、名前/PIN形式検証、同時作成競合、共有レート制限、PIN未設定・不正設定、入力PINが参加者DBへ保存されないこと、およびPIN・ハッシュ・秘密値がログやAPIレスポンスへ出ないことを確認する。同名別人や同名PIN衝突のシナリオは対象外。
   - Cookieは発行、照会、省略ログイン、改ざん・期限切れ・参加者削除・設定version不一致時の拒否、別参加時の削除、CSRF、Cookie属性を確認する。
   - 回答APIはCookieなしの拒否、本文participantIdの無視または拒否、新規回答へのparticipantId記録、旧匿名ログの保持を確認する。
   - UI/E2Eは初回フォーム、案内の読みやすさ、Cookie照会中の安定した表示、認証済みの手動開始、別参加、回答途中の再ログイン、ホーム統計非表示と回答CTAを確認する。
   - 主催者向けに、催し共通PINの生成・KDFハッシュ化・秘密の環境設定への登録・参加者への案内・変更時の全セッション失効手順を追加する。平文PINは安全な方法で参加者へ案内し、ログやリポジトリに残さない。

## セキュリティとUX上の注意

- 催し共通4桁PINは参加受付の簡易確認であり、本人確認や強い認証ではない。同じ催しの参加者は同じPINを知る。小規模な催しでの利用を前提とし、別人の同名者を区別・排除する仕組みは作らない。
- 4桁PINの候補は10,000通りに限られる。サーバー設定にはsalt付きKDFハッシュを用い、共有レート制限を設けるが、これによって強い認証になるとは扱わない。PINの平文・ハッシュ・設定秘密値はログやクライアントに出さない。
- 名前と参加者の存在を不必要に列挙できるAPIを作らない。回答閲覧機能を追加する場合は、この計画とは別に認可設計を行う。
- Cookieは署名付きHttpOnly/SameSite=Laxとし、適切なPath・期限を付け、本番でSecureにする。署名鍵とPINハッシュは秘密の環境設定で管理する。Cookieだけでなく署名・期限・participant ID・参加者の有効性・設定versionを検証する。
- 期限は既定30日を例として催し期間に合わせられるようにする。共通PIN変更時は設定version更新により既存セッションを失効させる。
- 回答途中状態はリロードで復元しない。Cookie失効時は画面内stateを維持して再ログインに誘導し、再ログイン後の自動送信や回答の永続再開は追加しない。
- 参加者情報は目的に必要な最小限にする。削除・保持期間の運用が必要なら別途定義する。
- 開始画面に長い警告や過度なセキュリティ説明を置かず、参加に必要な短い案内を優先する。

## 非目標

- 参加者がPINを登録・変更・再発行する機能、参加者ごとのPIN、主催者向け管理UI。
- 催し共通4桁PINによる強い本人確認、メール/電話認証、パスワードアカウント化。
- 別人の同名者を区別すること、同名者間の衝突を解消するUX。
- 過去の匿名ログを回答者へ推定して割り当てること、既存ログの削除。
- 回答履歴を参加者に閲覧させる画面、ランキング、ユーザー別統計。
- 回答途中状態をlocalStorage等へ永続化・再開すること、自動回答再送。
- 出題・採点・5問フロー自体の変更。

## 完了条件

1. ホームに「これまでの回答状況」セクションと統計カードが表示されず、回答開始への主CTAがわかりやすい。
2. 初回画面は短い案内、名前、主催者が案内した催し共通4桁PINを一つのフォームにまとめ、「はじめる」操作で参加できる。参加者向けPIN作成・登録・再発行の導線はない。
3. PINはサーバー秘密設定のsalt付きKDFハッシュと照合され、未設定・不正設定時はfail closedとなる。参加者レコードはID、trim+NFC正規化名、表示名、作成日時だけを持つ。
4. 同じ正規化名は同一参加者として再利用され、同時登録でも重複レコードを作らない。別人同名を分離する要件はない。
5. セッションCookieは署名済みHttpOnly/SameSite=Lax、適切なPathと設定可能な期限を持ち、本番でSecureとなる。照会と保護APIは署名・ID・期限・有効参加者・設定versionを検証し、共通PIN変更後は既存Cookieが無効になる。
6. 有効Cookieが残っていれば名前とPINの再入力を省略し、「○○さん」と「検定をはじめる」を表示する。クイズは自動開始しない。別参加操作でCookieとクイズstateをリセットする。
7. 新しい `/api/answers` は有効Cookie必須で、本文のparticipantIdを使わない。新規回答には検証済みparticipantIdを保存し、過去ログは削除せずNULLを維持する。
8. 回答途中にCookieが無効になった場合は画面内の選択を保持して再ログインを促す。自動送信や永続再開は行わない。
9. PIN、ハッシュ、秘密値、Cookie値をログやlocalStorage/sessionStorageへ保存しない。セッションCookieはHttpOnly属性でブラウザーが保持する。レート制限は共有ストアを使い、正規化名ごとに既定5回/15分とする。送信元情報による制限は行わない。
10. `openspec/specs/stcirt/spec.md` のRequirements/API/Data Modelが実装と一致し、主催者向けに共通PINの設定・安全な案内・変更時のセッション失効手順が記載されている。
11. 名前正規化、同名再利用、PIN設定失敗、レート制限、Cookie照会・期限・設定version・CSRF、匿名POST拒否、migration互換性、UI/E2Eをテストで確認する。
