# OpenSpec Scenario とテストのトレーサビリティ

対象は [`openspec/specs/stcirt/spec.md`](../../openspec/specs/stcirt/spec.md) のR1–R9にある全35 Scenario（R1:3、R2:4、R3:3、R4:5、R5:4、R6:4、R7:3、R8:6、R9:3）。各行は Scenario 本文の WHEN/THEN を現行テストの assertion と照合した結果であり、名前の類似だけでは「直接」としていない。対応度は Scenario の主要条件を明示的に検証する「直接」、一部の条件だけ検証する「部分」、間接的な状態/helper 検査に留まる「推定」、該当 assertion を確認できない「未確認」。補助テストが同じ行にある場合も、主判定はその Scenario の担保範囲を示す。

**監査成果物の状態（2026-10-18）:** Plan79の静的条件・roster照合は完了し、後続の許可済み実装・検証結果を台帳とbacklogに反映した。最新の報告済み検証はVitest 9 files / 371 tests passed、Chromium targeted E2E 3 invocations / 3 passed（E2E78-19/20: 2 passed, 19.8s; E2E78-32: 1 passed, 8.1s）、presentation E2Eファイルのoxfmt check passed、oxlint exit 0（既存line 2923にwarning）、`git diff --check` passed。ID-only grepのno-tests-foundはテストを実行しておらず失敗runに数えない。この限定結果は全条件の実証を意味しない。残件はB79-08の実支援技術/deviceおよび200% physical zoom、B79-12のJEV運用owner・production scheduler/secret/monitoring・provider環境確認。これらはコーディングエージェントが実証できない人手/外部環境残件として意図的にOpenを維持し、静的成果物完了を妨げない。B79-02はR8-S6の既存Chromium computed style/timing（E2E78-19/20）とR9 test-SQLite統合証跡の条件別マッピングを終えてクローズした。B79-04は127 unique condition treatmentsの静的マッピング成果物として完了したが、127条件すべての行動を保証したという意味ではない。詳細と過去runは[監査台帳](spec-test-coverage-audit-ledger.md)および[backlog](spec-test-coverage-audit-backlog.md)を参照。

## Scenario coverage から分離するテストと保証範囲

- **補助的なspec関連テスト:** `tests/answer/*`, `tests/app/answer/*`, `tests/components/*`, `tests/app/presentation/*` の多くは状態遷移・アクセシビリティ・描画を細かく支えるが、API認証や永続化を単独では保証しない。`tests/api/*` はroute boundary、`tests/db/*` は一時SQLite上のrepository/transaction boundaryを補完する。
- **E2E mock境界:** Plan78のPlaywright fixtureは通常 `/api/**` をstubし、allowlist対象以外の未処理APIを遮断する。各specが `page.route` で応答を用意するケースは画面・ブラウザ動作の検査であり、実API/DB persistenceの証明ではない。`presentation-session.spec.ts` はfixtureの明示allowlistだけでsession routeを実行する部分がある一方、別テスト自身のroute mockがあればhandlerを通らない。詳細は [`shared-plan78-test-meaningfulness-review-ledger.md`](shared-plan78-test-meaningfulness-review-ledger.md) のE2E inventoryを参照。
- **DB不変条件:** schema uniqueness/FK、owner-target一対一、revision/idempotency、submission-version整合、snapshot replacement/rollback、visibility serialization、ranking tie rulesなど、Scenario文面のUI/API結果を直接試さないDB固有のassertionは、対応Scenarioの補強には使うが独立したScenario coverageとして数えない。
- **helper/tooling tests:** `tests/lib/*`, `tests/presentation/*` の純helper、`tests/scripts/*`, migration/bootstrap、coverage/security/spec-ref toolingは、Scenario固有の実行経路を通らない限り仕様カバレッジに含めない。
- **benchmark / retired tests:** `tests/db/*.bench.ts` と `shared-plan78-benchmark-ledger.md` の `BENCH-*` はローカルSQLite/In-processの計測・fixture整合確認で、仕様Scenario検証や本番性能保証ではない。runtime manifestのRetired節に載る旧test/helperも現行カバレッジに数えない。

### 明示的なspec/test gap または追加の assertion 確認が必要な点

- R1-S1の不正batch全形（duplicate/out-of-order/malformed/unavailable）をひとつずつ分けたcurrent assertion、およびanswer-key等の禁止fieldをquestion route/clientの両境界で独立検証する範囲。
- R2-S4のvisibility show/hide/re-showとanswer writeの全競合順序、およびowner/assistedの双方について同一transaction規則が守られる全ケース。
- R4-S4でparticipant PIN/secret rotation、全protected endpoint拒否、same-person explicit retry、別participantへのdraft非継承をまとめた統合経路。
- R5-S1の200% zoomを含む全answer状態、R5-S4のspinner厳密なCSS寸法/currentColor/reduced-motion computed style。
- R6-S3/S4のadmin protected API 401後のmemory deck clear、transient readごとのretention、期限切れcookieを使う実browser統合。
- R7-S2でversion mapのmissing/unknown/unsupportedすべてとexcluded reason count overlapを組み合わせた集約ケース。R7-S3のtransport retry envelope、operation ID保持、新snapshot revisionとのrace全組合せ。
- R8-S4/S5の全stage・ordinal・modifier/repeat/interactive target・gesture組合せ、および実支援技術でのannouncement確認。

上記は台帳のhistorical pass結果から「未実装」と断定したものではなく、この照合で個別 assertion を確証できなかった範囲。 coverage tier/statement coverage、過去のplan78件数、benchmark値も要件網羅の代用にはならない。
