# Specification management

## Sources of truth

- `openspec/specs/stcirt/spec.md` is the sole product requirement and API contract. Keep its existing R1–R9 identifiers stable. It records agreed behavior, references implementation evidence, and calls out missing evidence; a code observation alone does not create a new requirement.
- `README.md` is the user and developer entry point and links to the maintained material.
- `src/lib/codemap.md`, `src/lib/db/codemap.md`, and `src/app/codemap.md` are code navigation aids, not requirement sources.
- `docs/operations/`, `docs/data-governance.md`, and `docs/decisions/` hold procedural guidance, lifecycle questions, and decision records. They must link back to the spec and label unknown facts as unresolved.
- `shared_plan/` is ignored work-planning storage. Never keep the only copy of an agreed requirement or decision there.

## Ownership and change flow

The product owner role approves product behavior and user-visible guarantees. The application maintainer role confirms implementation and test evidence. The deployment/operator role owns external service and recovery procedures. Assign named people through the project’s normal process; no individual owner is assumed here.

For an API, data-model, authorization, UI, or external-dependency change, update the relevant R requirement and API/data/component contract in the same change. Add or revise a concrete Scenario, then update the evidence row below with the implementation path and tests that actually assert the behavior. Record absent tests as gaps. For documentation-only corrections, keep the observation separate from a requirement change. A requirement or guarantee change needs product-owner agreement before it is presented as agreed behavior.

### Evidence gaps that remain

- R5's mobile/keyboard behavior has browser tests, but repository tests do not establish full assistive-technology support or the complete 200% zoom/reduced-motion matrix. Those claims need manual accessibility review in representative browsers/assistive technology.
- The repository has no scheduler configuration or test proving deployed JEV retry cadence, alerting, or completion time. The unit/API tests can only establish the worker behavior invoked in-process.
- No repository test establishes backup/restore success, retention/deletion propagation, production capacity, remote Turso round-trip latency, or a production availability/p95 target. These remain decisions and operational evidence gaps rather than test failures.
- The source test paths above are traceability starting points. A future requirement change must inspect the assertions for the changed clause; broad suite pass or coverage percentage alone cannot close these gaps.

## Spec decomposition and checker decision

This review keeps one canonical `openspec/specs/stcirt/spec.md` and R1–R9 because the existing product contract is cohesive and the fixed-path hooks/CI already name that single file. Splitting it now would require coordinated changes across `scripts/check-spec-update.sh`, `scripts/check-spec-refs.sh`, `openspec/config.yaml`, `AGENTS.md`, README, CI, and hooks, with no demonstrated benefit. The current reference checker has documented limits: absent spec passes, wildcards are skipped, and only backtick-quoted `src/` and `tests/` paths are checked. This plan does not silently change that behavior; making missing spec or coverage gaps blocking is a separate workflow decision. No CLI installation or checker hardening is included.

## Validation record

The repository workflows remain the validation source: pre-commit, pre-push, and `.github/workflows/main.yml`. The baseline for this documentation implementation was HEAD `35d1c57` with a clean worktree at initial inspection. `scripts/check-spec-update.sh` warns when selected source changes are staged without the fixed spec path; it is non-blocking. `scripts/check-spec-refs.sh` checks backtick-quoted `src/` and `tests/` references in that fixed spec, but skips wildcard references and succeeds when the spec is missing. Neither script validates requirement completeness or OpenSpec syntax.

No OpenSpec CLI dependency is declared in `package.json` or the lockfile, and there is no local `node_modules/.bin/openspec`. The globally installed OpenSpec CLI is version 1.5.0; `openspec schemas` lists `spec-driven`, matching `openspec/config.yaml`. No project-specific schema file is checked in. OpenSpec validation is not registered in package scripts, hooks, or CI, so the validation below is a review check and does not establish a repository gate.
