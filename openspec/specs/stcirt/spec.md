# Stcirt Five-Question Exam Specification

## Purpose

Stcirt presents four multiple-choice questions and one free-response question in ID order. Participants join with a display name and the event's shared four-digit PIN; a signed HttpOnly cookie identifies them for subsequent answers. The exam UI and exam-time APIs do not disclose correctness, explanations, scores, rubric details, JEV responses, or assessment state. Legacy `questions` and `answer_logs` data remain intact and are not read or written by this application. There is no home UI; `/` redirects to `/answer`.

## Data Model

The Drizzle schema in `src/lib/db/schema.ts` contains the legacy tables and the exam-specific tables:

- `knowledge`: source text and title for stored learning material
- `questions`: one question per knowledge record, with choices and correct answer
- `answer_logs`: submitted choices, correctness, and answer time
- `exam_questions`: stable integer IDs and unique keys for the five seeded exam questions, each with an explicit `question_version`
- `exam_participants`: unique trim+NFC normalized name, display name, and creation time; no PIN data
- `assisted_participants`: one assisted-answer target per owner (`owner_participant_id` primary key) and at most one owner per target (`target_participant_id` unique), both referencing `exam_participants`; target creation and relationship insertion are atomic
- `assisted_result_shares`: at most one share per owner and per assisted target, with a unique SHA-256 `token_hash`, UTC issue/expiry timestamps, and cascading participant foreign keys; the raw bearer token is never persisted
- `exam_answer_logs`: submitted choices, correctness, answer time, and nullable participant reference; historical anonymous rows remain NULL
- `exam_answer_submissions`: participant-owned fixed five-question submissions, revision, and the `question_versions` map captured when saved
- `exam_submission_answers`: current selected answers or free text; legacy fifth-question selections keep an explicit `legacy` kind and are never converted or regraded
- `exam_answer_assessments`: current fifth-question revision and `question_version`, durable retry state, raw/normalized scores, confidence, model, `rubric_version`, attempts, and graded time
- `exam_submission_operations`: operation IDs and canonical payloads used for idempotent retries and mismatch rejection
- `participant_rate_limits`: shared database-backed failed-authentication windows keyed by HMAC fingerprints, without storing IP addresses or names
- `presentation_sessions`: singleton current presentation state, progression version, snapshot generation (`snapshot_revision`, zero until explicitly aggregated), `question_versions` and `rubric_versions` maps captured by aggregation, current zero-based question index, and durable `projection_hidden` standby flag. These maps are the version snapshot. The legacy `presentation_mode` column remains for existing databases but does not affect presentation behavior.
- `presentation_questions`: shared presentation and participant-results question/choice/correct-answer/explanation/version snapshot replaced atomically by the administrator's explicit aggregate action in `exam_questions.id ASC` order
- `presentation_entries`: shared presentation and participant-results participant/display-name/floating-point score/standard-competition-rank, aggregation-target flag, and typed answer/assessment snapshot for every participant; replaced atomically only by explicit aggregation. Only participants with a selected complete submission compatible with the snapshot's current question and assessment versions are aggregation targets; other participants remain in the snapshot with score zero and no rank.
- `presentation_operations`: an internal idempotency-token ledger for admin writes. Position entries encode the requested state/index only to reject operation-ID reuse with a different target; they are not read as presentation history, and coalesced unsent positions create no ledger entry. The legacy optional mode payload remains for existing rows but is no longer written or interpreted.
- `participant_result_settings`: singleton durable participant-results visibility (`visible`) and publication-history (`ever_published`) flags, independent of presentation stage and projection visibility. `ever_published` defaults to false, becomes true after successful publication, and remains true when results are hidden

Migration 0019 adds `assisted_result_shares`. Share rows are deleted when either related participant is deleted. The 30-day lifetime is the initial product policy; reissue rotates the hash and expiry in one owner-keyed upsert, invalidating the prior URL.

The matching application/API types are defined alongside their boundaries: `AnswerBatchInput`, `AnswerBatchResult`, and `AnswerSubmission` in `src/lib/api/client.ts`; request/result schemas in `src/lib/api/schemas.ts`; `ParticipantResult` and `ParticipantResultQuestion` in `src/lib/participant-results-contract.ts`; and `PresentationState`, `PresentationAction`, and `PresentationAnswerSnapshot` in `src/lib/db/repository/presentation-repository.reads.ts`. These are the client and service contracts; persisted records remain the Drizzle tables above rather than a second hand-maintained data model.

Migration 0013 adds `presentation_sessions.snapshot_revision`: rows with a prior snapshot or started state become revision 1, including valid empty snapshots, while sessions without a snapshot remain revision 0. Participant names are trimmed and normalized to Unicode NFC for case-sensitive uniqueness. They are not compatibility-normalized and internal whitespace is preserved. The shared event PIN and session signing secret are held only in server-side environment configuration.

Migration 0015 adds `assisted_participants`. The owner is a participant with a completed submission; the target is a separately created `exam_participants` row whose answers are saved in the existing participant-owned submission tables. The relationship does not replace or alter the owner's participant cookie or submission.

Migration 0016 adds question-version columns to exam questions, submissions, assessments, and presentation sessions. It assigns explicit versions to the five current seeded questions but does not backfill historical submissions, assessments, or presentation snapshots; those old records remain unversioned and fail closed where version consistency is required.

The fifth seeded exam question (`exam_questions.id = 5`, key `it-literacy-005`) is a free-response question: `2023年3月に珠美が物価高に耐えられず起こした行動は？`. Its model answer is `卵の値上がりが許せなかったため、春闘の賃上げが十分でないと卵を買わないと宣言し、実際に要求内容から一時金などが削られてしまったため、しばらく卵を買わなかった`.

Question text, expected answer, and grading rubric are versioned as a pair. The current Q5 pair is `questionVersion = tamami-egg-v1` and `rubricVersion = jev-q5-keywords30-30-jev40-v1`. The question version and expected answer remain stable; the rubric identifies the weighted scoring semantics. The JEV meaning rubric continues to assess accuracy and sufficiency, while the local assessment save combines its raw 0–9 score with binary egg and spring wage negotiation keyword hits at 30% each and JEV meaning at 40%. Assessment `raw_score` preserves the JEV raw score; `normalized_score` stores the complete Q5 total on 0–1. Submission `questionVersions` are captured at save time, and assessment records retain `questionVersion` and `rubricVersion`. Historical rows are not silently backfilled as current: prior assessments retain their original raw and normalized scores, and older or unknown rubric versions remain incompatible until a current assessment is recorded. Aggregation excludes completed submissions with missing/outdated question-version maps and excludes submissions whose Q5 assessment has missing/incompatible question or rubric versions. It records exact current `questionVersions` and `rubricVersions` maps in the presentation session and reports included and excluded counts; exclusion reason counts may overlap. A compatible assessment that is missing, ungraded, or stale for the current submission revision remains a readiness conflict. Unsupported current question/rubric registry versions remain a conflict. `start` rejects snapshots with absent or mismatched version maps; a new explicit aggregate is required to create a valid snapshot.

Unconfirmed answers are held in client state. In-progress assisted-answer drafts are additionally held in the current tab's `sessionStorage` for up to 24 hours from the latest draft update. Each record carries schema version 1, an expiry timestamp, and the assisted participant ID; expired records, unsupported schema versions, malformed records, and records for another assisted participant are purged before restoration. A successful assisted submission, a completed assisted reload, participant/account switching, an absent participant session, and an explicit 401/403 from participant-session, assisted-status, or latest-answer authorization also purge the draft. Latest-answer 401 enters reauthentication and 403 remains a retryable lookup error. A transient network or malformed-success response during participant-session, assisted-status, or latest-answer lookup is retryable and retains the draft for later recovery. Confirmed answer sets are persisted as participant-owned submissions and can be revised in place through the batch answer API. The `exam_answer_logs` table remains in the database schema, but current batch submissions do not append to it. A new migration updates question 5 and marks existing fifth-question rows as legacy without guessed conversion. Migration 0011 resets the assessment dataset by deleting prior answer logs and submissions and deleting the current presentation session (which cascades to its question and participant snapshots); it also returns participant-result publication to private. It retains `presentation_operations` so delayed retries of prior administrative operations remain idempotently rejected. Migration 0012 adds `participant_result_settings.ever_published` and backfills every existing visibility-settings row to true. The UI writes a false row only when hiding results after publication; an exceptional direct/API false write before publication cannot be distinguished from that normal history, so it is conservatively treated as previously published. Earlier migrations are immutable. `/` redirects to `/answer`; no home briefing or home navigation is part of the participant experience.

## Requirements

### Requirement: R1: Fixed five-question set

The participant client MUST check authentication and saved-submission state before starting an attempt, and MUST start only with the complete fixed five-question batch.

#### Scenario: [R1-S1] Start only from a complete ordered batch

- WHEN latest-submission lookup returns no saved submission and the batch endpoint returns exactly five unique questions in ascending ID order
- THEN the client may begin the exam with those questions, and the batch contains no answer key or grading fields
- WHEN the batch is incomplete, malformed, or unavailable
- THEN the exam does not begin and the participant can retry

#### Scenario: [R1-S2] Refuse an incomplete batch

- WHEN `/api/questions/batch` returns fewer than five questions
- THEN `/answer` keeps the question screen closed and offers a retry action

#### Scenario: [R1-S3] Do not treat a failed saved-submission lookup as a new attempt

- WHEN the latest-submission lookup fails after participant authentication
- THEN the client reports a retryable lookup failure and does not fetch questions as if no submission existed
- WHEN a saved submission is returned
- THEN completion is shown instead of starting a new exam

**WHEN** an unauthenticated user opens `/answer`, or an authenticated participant has no saved submission
**THEN** the client checks the participant session and latest submission before fetching the fixed five-question set in one request.

- The client requests `GET /api/questions/batch` once. The valid exam payload is exactly the first five dedicated exam questions in `exam_questions.id ASC` order.
- The batch question payload contains only `id`, `question`, `choices`, and `answerType`; it never exposes correct answers, explanations, or assessment data.
- The client starts the exam only when the response contains exactly five questions with unique, strictly increasing IDs. A request failure or incomplete, duplicate, or out-of-order batch does not start an exam and offers retry.
- The client creates a new submission ID and starts fetching questions only after latest-submission lookup returns `{ submission: null }`.
- The question screen appears only after the valid five-question batch has been loaded.
- A remount or reload first checks the participant's latest submission. A saved submission opens completion; no saved submission starts a fresh attempt.
- A batch request or payload validation failure is retryable; a partial response is never used to begin the exam.
- A latest-submission request failure is shown with a retry action and is never treated as an empty submission.
- If fewer than five questions are available, `/answer` does not start the exam and shows a retryable load error.

### Requirement: R2: Participant-authenticated answer confirmation and recording

The answer API MUST atomically save a confirmed five-question answer set for the authenticated participant and MUST NOT return grading data.

The participant UI MUST disable correction while results are visible, for both the participant's own submission and an owner-resolved assisted submission. Visibility is advisory for writes: a stale or direct request may still save when ownership, operation ID, and expected revision are valid. Initial submissions remain available. Answer writes do not serialize with publication visibility transitions. Snapshot aggregation and refresh timing are unchanged; saves after aggregation may remain absent from published results until an explicit aggregation.

#### Scenario: [R2-S1] Save one authenticated five-question answer set

- WHEN a participant with a valid signed cookie confirms a five-question answer set (four selected choices and one non-empty Q5 free-text answer) using a new operation ID and the current expected revision
- THEN all answers and the next revision are saved atomically, and the response contains no grading data
- WHEN the same operation ID and canonical payload is retried after a transport failure
- THEN the original revision is returned without a second write or assessment start
- WHEN the participant is missing, the Origin is invalid, or the request body is invalid
- THEN the request fails with the documented status and no partial answer set is committed

#### Scenario: [R2-S2] Reject a missing or non-owned submission

- WHEN a valid participant requests a missing or non-owned submission through `GET /api/answers/batch`, or tries to revise a submission owned by another participant
- THEN the request returns 404 without exposing or changing that submission

#### Scenario: [R2-S3] Reject stale and conflicting concurrent writes

- WHEN two corrections use the same expected revision and only one commits first
- THEN the other correction receives 409 and does not overwrite the committed answer set
- WHEN an operation ID is reused with a different canonical payload
- THEN the request receives 409

#### Scenario: [R2-S4] Keep publication visibility advisory for answer writes

- WHEN results are visible and a participant's UI shows a saved submission
- THEN the UI disables correction, while the answer API does not use visibility as a write authorization check
- WHEN a stale client or direct request submits a correction while results are visible
- THEN the write may succeed if ownership, operation ID, and expected revision are valid
- WHEN an already committed operation ID is retried with the same canonical payload
- THEN the original successful result is returned idempotently without another write, independent of publication visibility
- WHEN an answer write completes after the results snapshot was aggregated
- THEN publication visibility and the snapshot remain unchanged; the displayed result may remain stale until an explicit aggregation

**WHEN** a user chooses options for the five questions and confirms the set
**THEN** `POST /api/answers/batch` atomically saves the five answers for one stable submission.

- The user first joins with a display name and event-wide four-ASCII-digit PIN. A valid existing participant session may be reused without re-entry.
- During answering, show a read-only exam-style name field with `氏名` and the registered answerer's name. For the owner, show only the name without a `本人の回答` label; for an assisted answerer, use `代理回答` wording, using the existing identity resolution and fallback. Switching answer scope updates this display; the name is not editable here.
- Every batch answer POST requires a valid signed participant cookie and same-origin `Origin`; anonymous POSTs are rejected.
- The participant ID comes only from the validated cookie. A client-supplied `participantId` is rejected.
- A batch submission is associated with the validated participant. Historical single-answer rows remain unchanged with a NULL participant ID.

- Individual choices remain in client state until explicit batch confirmation; they do not create server records.
- Choices are native radio inputs grouped by question with a fieldset and legend; show each question prompt visually only in its heading and visually hide the duplicate legend while retaining it as the radio group's accessible name. Each input has an explicit full-row label, and its submitted value remains the existing shuffled-choice index.
- A pending batch request locks all answer controls and prevents duplicate submission.
- While pending, selected radios remain checked; the confirmation action communicates its disabled state to assistive technology and guards submission synchronously.
- The five selected choices remain available after a failed request so the user can retry.
- Questions 1–4 accept selected indices; question 5 accepts only trimmed non-empty free text up to 1000 characters. The server validates each variant against the stored question key.
- Each submission stores the `questionVersions` map that was current when the answer set was saved. Missing or unknown Q5 versions cannot be silently interpreted as the current question.
- Saving free text creates a durable pending assessment for that same submission revision in the answer transaction. After the save commits, the batch route uses Next.js `after()` to start only that submission revision's job through the atomic-claim worker, processing at most one job without delaying the response. If `TYPESAFE_API_KEY` is absent or post-response scheduling/worker startup fails, the durable job remains available for the manual retry endpoint; safe fixed-reason logs contain no key or exception details. Assessment state and results are not returned by the exam API.
- The grader accepts only the supported question/rubric version pair. A missing, unknown, or mismatched pair is rejected before provider grading and cannot produce a graded assessment.
- A successful batch confirmation moves to completion. The completion view can restore the saved five answers and revise the same submission.
- Show `回答済み` as a save-confirmation message only after a successful POST has a matching submission ID and accepted revision, or a saved submission has been fully validated and restored. `complete` phase, a submission ID, or a previous success alone is not sufficient. Restore errors, response ID mismatch, and invalid saved data after a 409 keep recovery guidance visible without the success message. A correction action is rendered only when saved answers were restored without error, publication is confirmed as waiting, and the answer batch is unlocked.
- An authenticated revisit or reload with a saved submission remains on completion. Its correction action restores saved selected indices to the shuffled choices and restores free text.
- If the saved submission is incomplete, malformed, or does not match the current questions, completion remains visible and correction is unavailable; no new submission is started and no old answer is overwritten.
- The UI does not use the response's correctness, correct index, or explanation fields. It shows no per-exam correctness, explanation, score, accuracy, or pass/fail state.
- While a saved submission is active in the answering or completed screen, the client refreshes publication/edit-lock state every 30 seconds. Initial state load and returning to a visible tab trigger an immediate refresh. Publication state disables editing in the UI; it is advisory for writes, while ownership, operation ID, and revision checks remain authoritative on the server.
- Retrying a batch after a transport failure reuses the operation ID and exact payload, so a committed request is returned idempotently without duplicating writes.
- When the validated participant cookie belongs to an owner who has an assisted target, `scope=assisted` resolves that target server-side for latest, restore, and batch-save operations; the client cannot provide a target participant ID.
- The assisted target uses the same fixed question set, submission validation, revision checks, and durable assessment behavior as a normal participant. Owner and target submissions remain separate and the owner cookie remains valid throughout.

### Requirement: R3: Completion

The participant client MUST show completion for an existing saved submission and MUST preserve that submission when correction is unavailable or not requested.

On `/answer`, the participant-results lookup gates publication-dependent controls on the completion surface. Keep publication state (`unknown`, `waiting`, `unavailable`, or `visible`) separate from lookup communication state. Until a valid publication response is confirmed, do not expose publication-dependent correction or result CTAs. A first lookup that is pending shows one polite status; a network, non-401 HTTP, malformed-payload, or read-timeout failure keeps publication `unknown`, ends the spinner, and shows static retry guidance with a manual GET-only retry. The retry is single-flight and never resubmits answers. A 401 or existing reauthentication state prioritizes participant recovery. After confirmation, visibility-resume refreshes and transient errors retain the completion view and last confirmed CTA quietly. Confirmation is scoped to participant ID and owner/assisted mode; stale requests and timers cannot update a changed scope. This is independent from the editing lock owned by `useSubmissionVisibility`.

While exam questions are initially loading, show one short polite status outside an `aria-busy` content region and an `aria-hidden`, noninteractive skeleton approximating all five questions and the final confirmation area. Do not add a minimum display time. While the answer POST remains pending, retain the selected answers and immediate submission lock. Do not add threshold-based long-wait copy until measured POST distributions show it is needed. After save confirmation, a small `/answer` completion heading may use React `<ViewTransition>`; keep saving, publication requests, status announcements, links, focus, and controls outside animation timing. Unsupported browsers render the same content without animation, and reduced-motion preference disables view-transition animation.

#### Scenario: [R3-S1] Restore a saved submission

- WHEN an authenticated participant returns with a complete saved answer set matching the current exam
- THEN completion is shown and correction restores that same submission
- WHEN the saved set cannot be safely restored
- THEN completion remains visible and correction is unavailable

#### Scenario: [R3-S2] Preserve a legacy fifth answer during correction

- WHEN the saved fifth answer has the recognized historical choice-shaped form
- THEN completion preserves it as legacy, correction treats Q5 as unanswered, and only a replacement free-text value may be submitted

#### Scenario: [R3-S3] Keep an assisted target separate from its owner

- WHEN an eligible completed owner registers the same target name again
- THEN the existing target is returned without replacing the owner cookie or creating a second target
- WHEN the owner requests a different target after a link exists
- THEN registration returns 409 and the original target remains linked

**WHEN** the batch answer POST succeeds with its requested submission ID and updated revision, or the latest-submission lookup finds an existing submission whose full saved answer set passes restoration validation
**THEN** show `回答済み` and offer `回答を修正する` only when the saved set can be safely restored.

- Completion has no score, correctness, explanation, or pass/fail result.
- Show the same read-only exam-style `氏名` field and owner/assisted label behavior as during answering, using the registered answerer's name and the existing assisted fallback. The owner has no `本人の回答` label; an assisted answerer has the `代理回答` label. Do not provide name editing on completion.
- The saved submission revision is updated in place when corrections are confirmed.
- When results are visible, hide the answer-correction button for both owner and assisted submissions, and hide all assisted-answer actions on the owner's completion view. A stale or direct request can still save if its owner and revision are valid; this is a UI control only.
- Show the answer-correction button and its correction guidance only after the participant-results request confirms `waiting` and the batch submission check confirms `unlocked`. Keep both hidden while either state is unknown or when the batch check is locked. Treat both `visible` and `unavailable` as published for hiding correction and assisted-answer actions; `unavailable` is not evidence that results remain private.
- Saved answers must match the current five-question ID set and answer types, with valid selected-choice indices or non-empty free text, before correction is enabled. If restoration fails, keep the completion screen and disable correction.
- A known legacy choice-shaped answer for the current fifth free-response question is a supported historical format, not a malformed current answer. Preserve it as legacy without converting or regrading its value, and allow completion and correction.
- When correcting a submission with that legacy fifth answer, treat the fifth question as unanswered and require a new non-empty free-text response of at most 1000 characters. Submit only the new free text; never resend the legacy selected value.
- A successful answer POST must return the requested submission ID. If the response identifies another submission, keep completion visible and disable correction.
- The question-loading skeleton approximates all five question cards and the final confirmation area, is noninteractive and hidden from assistive technology, and leaves its single status outside the busy region. Do not add long-wait copy until measured POST distributions show that it is needed.
- A small completion heading may animate after independently confirmed saving with React `<ViewTransition>`; publication GETs, submission controls, `useLinkStatus`, announcements, and focus remain independent. Unsupported browsers and reduced-motion preference use the same nonanimated content.
- When the owner has no assisted target, show `代理回答を行う` on the shared completion view, removing the manual publication-status refresh action. The button opens the dedicated assisted-name form, labeled `本来回答する人のお名前`, which accepts a name only and does not request a PIN or replace the owner session.
- After a target is registered and results are private, show `代理回答を修正する`. This resumes the same target; its name cannot be changed and no second target can be registered for that owner. Restore its selections, free text, legacy answer IDs, answered count, submission ID, and revision, then enter its editor directly without another name-entry or completion step.
- An owner can create an assisted target only after completing their own submission and only if they are not themselves another participant's assisted target. The target's normalized name must be unique across participants and differ from the owner's name. Repeating the same owner/name request is idempotent; a different name for an already linked owner returns 409.
- A registered target can resume an incomplete answer on reload or revisit, and can restore and revise a completed submission. A valid assisted draft survives reload in assisted scope for at most 24 hours since its latest edit, and restoration requires schema version 1 and a matching assisted participant ID. Expired, unknown-version, malformed, or wrong-participant drafts are purged and never restored. Successful assisted submission, completed assisted reload, participant/account switching, absent participant session, and explicit participant-session, assisted-status, or latest-answer 401/403 purge the draft. Latest-answer 401 enters reauthentication and 403 remains a retryable lookup error. A transient network or malformed-success latest-answer response retains the draft while the client waits for retry. Reloading a completed assisted submission without an in-progress draft clears completed assisted draft data and returns to the owner's completion view. Returning to the owner view preserves the owner cookie and submission. An assisted target cannot create another assisted target.
- The target's submission is distinct from the owner's and persists across route changes and reloads. If the target signs in later through the regular shared-PIN flow, the same participant record and submission are used.
- After an assisted target confirms answers, return to the owner's completion view after the save is confirmed. Keep the owner's saved answers and submission unchanged. Report an owner reload failure separately from a failed assisted save. A response whose submission ID differs from the requested ID is not a successful save.
- Use `代理回答` consistently for user-facing assisted-answer labels and actions; retain internal `scope=assisted` and persisted/API identifiers.
- When the assisted target has a submission, provide a link from the owner's completion view to the assisted result. Do not show that link before the target submits.

### Requirement: R4: Home and participant entry

The root route MUST redirect to participant entry, and participant sign-in MUST resolve the participant's saved state before the exam begins.

#### Scenario: [R4-S1] Use the compatibility route

- WHEN a visitor opens `/`
- THEN the server redirects to `/answer` without rendering home statistics
- WHEN a participant submits a valid display name and event PIN
- THEN the client checks that participant's latest submission before showing the exam or completion view

#### Scenario: [R4-S2] Reject invalid participant sign-in

- WHEN a participant submits a malformed or incorrect PIN, or the request has an invalid Origin
- THEN no participant session is issued and the quiz does not start

#### Scenario: [R4-S3] Resume the participant's existing state

- WHEN sign-in succeeds and the latest-submission endpoint returns a saved submission
- THEN the app enters completion rather than creating a second submission or loading a new question set

#### Scenario: [R4-S4] Expired or revoked participant sessions require explicit recovery

- WHEN a participant cookie is expired, invalid, or signed under a participant PIN/secret that has since changed
- THEN protected participant requests reject it and the answer flow requires reauthentication
- WHEN the same participant reauthenticates after an answer-save 401
- THEN the draft may be preserved for that participant, but the participant must explicitly resubmit it; a different participant does not inherit the draft

#### Scenario: [R4-S5] Rate-limit failed participant sign-in by normalized name

- WHEN failed sign-in attempts for one normalized name reach the configured limit (default five in a 15-minute window)
- THEN further sign-in attempts for that name are rate-limited and include the retry time
- WHEN the limiter is unavailable
- THEN sign-in fails closed without issuing a session
- Answer APIs do not use this sign-in rate limiter.

**WHEN** the user visits `/`
**THEN** redirect to `/answer` without rendering home content or loading statistics.

- `/` remains a compatibility entry point only. Do not show a home briefing, statistics, or a link back to `/` in participant, administration, or presentation screens.
- The initial answer-entry form accepts a name and the organizer-provided shared four-digit PIN in one form. Immediately above the participant-name field, show `令和八年度第一回` followed by `しゅんたま検定`, with the decorative vermilion `しゅんたま / 検定` stamp at the upper right of this title area using the shared `/cert_stamp.png` asset and an 8-degree rotated appearance. Keep the stamp clear of the card heading, title, and input fields; hide it from assistive technology and disable pointer interaction. Below the four-digit PIN field, show `披露宴までに回答を完了させてください。自身で入力が難しい方の為の代理回答は自分の回答完了後に行えます。`. Show the title, stamp, and note only on the initial answer-entry form, not on reauthentication or participant-switch forms. Do not show the former generic name/PIN instruction. After authentication, the client checks latest submission and proceeds directly to quiz or completion without an intermediate ready screen.

### Requirement: R5: Accessible responsive interface

The participant interface MUST support the documented responsive layout, keyboard operation, accessible status communication, and focus behavior.

#### Scenario: [R5-S1] Navigate and answer with keyboard at narrow width

- WHEN a participant uses the answer flow at 320 CSS px width or 200% zoom
- THEN the content remains usable without horizontal scrolling, and keyboard focus can reach question navigation and answer controls
- WHEN reduced motion is requested
- THEN the answer interface respects that preference
- Shared loading spinners remain visible and keep their loading meaning, but stop rotating; nonessential shared-button and answer-choice transitions have a computed duration of `0s`. With no reduced-motion preference, their existing motion remains enabled.

#### Scenario: [R5-S2] Keep the answer flow usable during a failed submission

- WHEN submission is pending
- THEN selected answers remain checked, controls are disabled, and the polite status announces progress
- WHEN the request fails
- THEN the participant can retry without losing the selected answers

#### Scenario: [R5-S3] Preserve focus chosen by the participant

- WHEN focus has moved away from the confirmation action before the completion handoff
- THEN the completion view does not steal focus from the participant's selected destination
- WHEN keyboard focus is on the confirmation action at submission start
- THEN the documented focus handoff targets the confirmation/completion heading

#### Scenario: [R5-S4] Render the answer submission indicator accessibly

- WHEN an answer submission is pending
- THEN its small 16 CSS px spinner uses a 2 CSS px border that inherits the button text color, remains visible while decorative and hidden from assistive technology, and stops rotating when reduced motion is requested

- Use a restrained exam-paper visual style with the existing beige, navy, and gold palette, light surfaces, ink text, and subtle decorative framing; keep spacing consistent and align the answering navigation with the answer content width. Do not use medals, pass/fail imagery, or certificate visuals.
- Always use the light color palette regardless of the operating system's color-scheme preference.
- Provide readable contrast, visible keyboard focus, native radio semantics, live status updates, and textual progress labels so color is not the sole signal. Choice rows and the primary confirmation action have at least 44 CSS px of interaction height.
- During ordinary answering, announce answer progress through one concise polite header live region; keep the descriptive status and final-review count visible but non-live. Keep a polite live status while submitting or refreshing, and keep recovery errors assertive.
- Render the answerer's name as a semantic `dl` with `dt` (`氏名`) and `dd` (registered name). For the owner, show only the name; for an assisted answerer, accompany the name with the `代理回答` classification. Keep the field display-only and use a horizontal framed layout that wraps at narrow widths. Show the registered name without omission for ordinary registered names; no length limit or guarantee for exceptionally long names is specified.

### Requirement: R6: Isolated administrator authentication

Administrator access MUST use its separate signed session and MUST remain isolated from participant authentication.

#### Scenario: [R6-S1] Keep administrator access isolated

- WHEN an administrator signs in with valid admin configuration and PIN
- THEN a separate signed admin cookie authorizes protected admin requests
- WHEN participant credentials are used at an admin endpoint, admin configuration is missing, or the request lacks a valid cookie
- THEN protected admin access is denied

#### Scenario: [R6-S2] Reject invalid administrative mutations

- WHEN an otherwise valid administrator submits a mutation with a missing or cross-origin `Origin`
- THEN the mutation is rejected and the presentation/result visibility state is not changed
- WHEN the admin PIN is invalid
- THEN no admin cookie is issued

#### Scenario: [R6-S3] Clear private presenter data after session loss

- WHEN a protected presenter request returns 401
- THEN presenter controls and the in-memory private deck are cleared and polling waits for login or visible resume
- WHEN a protected read fails transiently without 401
- THEN the latest valid displayed state is retained for retry

#### Scenario: [R6-S4] Reject an expired administrator session

- WHEN an administrator cookie is expired, malformed, or cannot be verified
- THEN protected admin requests are unauthorized and presenter private data is cleared after a 401

- Admin sign-in uses `ADMIN_PRESENTATION_PIN` and `ADMIN_PRESENTATION_SESSION_SECRET`; if either is missing or invalid, admin sign-in and protected admin endpoints fail closed.
- The admin session is a signed HttpOnly cookie with a purpose-specific HMAC key, separate cookie name and secret from the participant session. Participant cookies never grant admin access.
- `POST` and `DELETE` admin session operations and every admin state mutation require a same-origin `Origin`. Every admin presentation route requires a valid admin cookie. Admin and public presentation API responses use `Cache-Control: no-store`.
- `/admin/presentation` is the PIN entry point and remains open after successful authentication. It re-fetches presentation state, provides start, opens or returns to the named presenter tab, and controls result publication. It has no projection hide/show control. Participant-result visibility status and its publish/hide control remain available in every presentation state; publishing is enabled only when an explicit aggregate snapshot is ready, while hiding remains available at any time. After a successful visibility change, if focus was on the activated publish/hide button and has not moved elsewhere, focus moves to the corresponding next available visibility action after refreshed state commits. Initial load never moves focus. After a retryable failure, focus returns to the same retry action after state refresh only if focus was on the trigger and has not moved; otherwise preserve the user's focus. Unauthorized failures clear controls without focus handoff. Before rendering `/presentation?presenter=1`, the server verifies that admin authentication is configured and the request has a valid admin session cookie; otherwise it redirects to `/admin/presentation`. The page also verifies `/api/admin/session` before enabling presenter controls. The query parameter requests presenter progression but never grants authorization.
- A 401 from a protected admin operation immediately removes presenter controls and clears the preloaded private deck from the screen. Private deck data is held only in presenter memory and is never written to browser storage.
- Admin and presenter polling runs only while `document.visibilityState` is `visible`; returning to visible starts an immediate refresh. Window focus by itself does not pause polling. The admin console confirms authentication on initial load and visible resume through one protected presentation-state GET. A successful read confirms authentication; a 401 clears admin state and stops polling until login or a visible-resume recheck. For another state-read failure at startup or visible resume, the console uses the session-only GET as a fallback to distinguish unconfigured/unauthenticated access from a retryable state failure. If that fallback also fails, it preserves any prior authentication state: an unknown initial state retries with a checked refresh, while a known-auth state retries with an ordinary presentation-state GET. The session endpoint is also used by the presenter page before enabling presenter controls.
- Presenter polling uses `GET /api/admin/presentation?view=controls` for ordinary refreshes and checks `GET /api/admin/session` only initially and on visible resume. A session or protected controls/deck 401 stops polling, removes presenter controls, and clears the private deck; polling resumes after login or a visible-resume recheck. Public projection polling continues in the background while its document is hidden.
- Admin and presenter polling schedule the next read only after the current read settles, and each polling loop has at most one active refresh. In the admin console, login and mutations wait for an active poll to settle; while they run, scheduled polls wait, so the poll and user operation do not start duplicate HTTP work. Presenter navigation changes the local slide immediately without waiting for an active poll or server response. It persists an absolute slide cursor through a single-flight, latest-wins background writer, coalescing intermediate slide positions; failed writes retain and retry the newest cursor. Poll responses that began before a local navigation, and polls overlapping pending cursor persistence, cannot roll the presenter back, including when a delayed response arrives after the write settles. A cursor-write 409 triggers controls/deck reconciliation. The newest queued cursor is retried only when its snapshot revision is unchanged and that exact state/index exists in the refreshed deck; if the snapshot revision changed, the old-deck cursor is discarded and the presenter adopts the refreshed server cursor. The presenter's eight-second timeout covers the complete serial session → controls → deck refresh, not eight seconds per request. Poll requests retry after timeout/failure and are aborted on unmount. Responses from canceled or superseded refreshes cannot update the screen or start later reads in the serial refresh. A failed read keeps the latest valid admin state or presenter deck/stage visible and reports that it is retrying. Invalid controls/deck/projection payloads are treated as failed reads rather than default state values. Presenter polling treats the protected GET endpoints' 401 response as authentication loss; network errors, timeouts, malformed data, and 5xx responses retain the displayed stage and retry. A 403 is not treated as authentication loss: it is used by authenticated mutation endpoints for invalid Origin and remains an operation failure.
- When presenter controls successfully report a new snapshot revision, the previous deck is known to be stale because aggregation can change questions, answers, scores, ranks, and names. The old slide is hidden while a matching deck is loaded; it is not restored if the deck fetch fails or returns another revision. Polling retries and progression remains disabled until controls and deck revisions match. This fail-closed handling applies only after authoritative controls confirm a revision mismatch; transient read failures without a confirmed newer revision keep the currently displayed stage.

### Requirement: R7: Presentation snapshot and ranking

The presentation MUST use an explicitly aggregated versioned snapshot and MUST preserve the prior snapshot when aggregation cannot safely update it.

#### Scenario: [R7-S1] Aggregate only by explicit administrator action

- WHEN an administrator aggregates a compatible answer set
- THEN a transaction replaces the shared snapshot and advances its revision
- WHEN presentation starts or participant results are published without a nonzero snapshot revision
- THEN the operation returns 409 and does not create a snapshot implicitly
- WHEN aggregation fails
- THEN the prior snapshot and presentation state remain intact

#### Scenario: [R7-S2] Exclude version-incompatible submissions and reject unready compatible assessments

- WHEN a completed submission has an incompatible question-version map, or its existing Q5 assessment has an incompatible question/rubric version
- THEN the submission is excluded from the aggregate candidate set
- WHEN no submission is included and at least one completed version-incompatible submission was excluded
- THEN aggregation succeeds with `snapshotUpdated: false` and preserves the current snapshot and revision
- WHEN a version-compatible submission has a missing, pending, failed, or stale-for-revision Q5 assessment
- THEN aggregation returns 409 and preserves the current snapshot
- WHEN the compatible assessment becomes ready
- THEN a later explicit aggregate may include that submission

#### Scenario: [R7-S3] Reject stale and replayed presentation operations safely

- WHEN an operation ID is replayed with its same action and payload
- THEN the recorded operation does not execute a second time
- WHEN an operation ID is reused with a different action, or presenter navigation uses a stale snapshot revision
- THEN the request returns 409 and does not apply the conflicting operation
- WHEN `advance` or `previous` reads an unsupported persisted presentation state
- THEN the request returns 409 with the generic message `Presentation state is invalid`, and leaves the session and operation history unchanged

- Only one current presentation session is stored. An explicit administrator aggregate action snapshots all `exam_questions` in `id ASC` order, all `exam_participants`, and each participant's latest valid complete saved submission against that question set in one database transaction. This is the only operation that creates or replaces the snapshot. Start, publication, republishing, answer updates, and stage navigation read the current snapshot without rebuilding it. A failed aggregate leaves the prior snapshot, state, cursor, visibility, and projection-hidden flag unchanged.
- A successful aggregate increments `snapshot_revision` and the normal operation `version`, while retaining the current state and cursor when the cursor remains valid. During ordinary presentation operation, if aggregation invalidates a `question` or `answer` cursor, correct it to `question` at index zero, or to `podium_preview` at index zero when there are no questions. This aggregate-time cursor correction is independent of the `start` and `reset` transitions, which enter `opening` at cursor zero. Preserve `not_started` and `finished` session states. Existing snapshots and started empty snapshots migrate as revision 1; sessions with no snapshot migrate as revision 0.
- Start and first or later publication require a nonzero snapshot revision and return 409 while unaggregated. Result visibility remains independent from `projection_hidden`, stage, and operation version. Hiding results and repeated already-public requests do not rebuild the snapshot. A later explicit aggregate updates the snapshot used by both the presentation and participant results without changing result visibility.
- Questions 1–4 award one point for a correct selection. Question 5's rubric-versioned `normalized_score` is the complete Q5 score (0–1), including any local keyword/JEV weighting already applied when the assessment was saved; aggregation never recomputes or reapplies that weighting. `raw_score` remains the JEV raw score for audit. Confidence is ignored. Existing assessment rows and snapshots retain their stored values until an explicit compatible aggregate commits; no historical assessment or rubric version is silently rewritten. Stored scores and rank comparisons retain floating-point precision; participant total scores, Q5 per-question normalized scores, and JEV raw similarity displays show exactly two decimal places. A legacy Q5 selected-answer record cannot be regraded or aggregated as a current free-text result; aggregation returns 409 and requires explicit audit or resubmission, while any prior snapshot remains unchanged. Legacy answers in an existing snapshot remain labeled legacy. Unanswered or invalid/incomplete submissions score zero. Every participant remains represented in the snapshot, but only participants with a selected complete submission compatible with the current question and assessment versions are aggregation targets and ranked; others have no rank. Ties among targets use exact score equality and standard competition ranking (1, 1, 3).
- Aggregation fails atomically while any otherwise version-compatible latest free-text submission has an assessment absent, pending, failed, or stale for its answer revision. Missing, old, unknown, or incompatible submission/assessment version pairs are excluded and counted by mismatch reason, rather than treated as readiness conflicts. If all complete submissions are excluded for version mismatch, aggregation succeeds with `snapshotUpdated: false` and preserves the preceding snapshot and revision. A stale or incompatible existing snapshot remains readable but cannot start under the current version map until a new compatible snapshot is explicitly aggregated.
- The presentation labels the existing correct-answer count as `ポイント` in the projection and authenticated admin list/preview; this is display wording only and does not change scoring.
- Rank announcement slides use the reference-based 16:9 gold double-line outer frame with corner ornaments; the A4 source reference remains unchanged, and the rank-specific metallic plate remains around the rank heading.
- A correct multiple-choice answer is identified by reversing the background and text colors across the full correct-choice row, including its label, body, and wrapped lines, and by the visible text label `正解`; correctness remains understandable without color. At the documented 1920×1080 CSS viewport (16:9 reference), normal question, choice, explanation, rank, name, score, and answer text must remain at least 20 pt (26.67 CSS px) after fitting. The regression measures each main text element's computed font size multiplied by the shared fit scale and converts CSS pixels to points at 0.75 pt per pixel. The layout must leave enough space for normal reference content to meet this target. The sole rank-screen exception applies only when exactly two winner cards are displayed and a long winner name or long free-text Q5 answer makes a shared fit reduction necessary to keep the complete rank slide inside its frame without overlap, omission, or clipping. Because fit uses one scale for the slide, this necessary reduction may also put other main text on that rank screen below 20 pt. Long content that fits without such a reduction, and all opening, question, answer, and other normal rank content, remains subject to the 20 pt target. An individual long answer detail may also use the narrowly scoped text ellipsis described in R8. No clipping or truncation is used to preserve a font size.
- In the public projection and authenticated admin preview, each rank stage shows its rank label once, followed by winners in HTML order. For one winner, the name is the largest text and the score is smaller supporting information. For a tie, each winner keeps the name and score paired in one item under the shared rank label. For result-announcement ranks, each name has a space before the `殿` honorific; the score remains `ポイント` rounded to two decimals. Names of up to seven Unicode code points stay on one line with the honorific. The display renders at most two winners per rank in source order and, when more are tied, shows `ほか N 名` with the same rank group. This is a display-only limit; projection data, scores, and ranks retain every tied participant.
- The score, rank, participant display name, selected-answer snapshot, question text, choices, correct answer, and non-empty snapshot explanation stay fixed until the next explicit aggregate. For a legacy snapshot with a null or blank explanation, the answer-stage projection uses the current `exam_questions.explanation` for its `sourceQuestionId` until aggregation captures the explanation; this fallback is never shown in the question stage. Later answer revisions and other question edits do not alter the snapshot before aggregation.
- Aggregation captures `questionVersions` and `rubricVersions` maps in the presentation session. A completed submission with a missing or outdated question-version map is excluded; a later compatible submission from the same participant may still be selected. A submission whose Q5 assessment has a missing or incompatible question/rubric version is also excluded; these reason counts may overlap, while the excluded submission count is unique. A newly recorded aggregate operation returns `snapshotUpdated`, `includedSubmissionCount`, `excludedSubmissionCount`, and `excludedReasonCounts` (`questionVersionMismatch` and `q5AssessmentVersionMismatch`) with its successful response. With at least one included submission, the partial result snapshot is committed and `snapshotUpdated` is true. If no submission is included because at least one completed version-incompatible submission was excluded, aggregation succeeds with `snapshotUpdated: false` and leaves the existing snapshot and revision unchanged. If there are no submissions or only structurally incomplete submissions, explicit empty aggregation proceeds as before and `snapshotUpdated` is true, including when there are no participants. A compatible assessment that is absent, ungraded, or stale for the current submission revision remains a 409 readiness conflict, as do unsupported current question/rubric registry versions and concurrent session/CAS conflicts. Starting a presentation with an old or incomplete version snapshot fails with a conflict until an explicit aggregate creates a valid snapshot. Existing rows are never assigned a version by inference or backfill.
- State progression is manual: `start` enters the `opening` cover at cursor zero; `advance` from opening enters `question` zero, or `podium_preview` at cursor zero when there are no questions. Each question advances `question` then `answer`; after the last answer, `podium_preview` announces no winners; ranks with no winners are skipped while announcing rank 3, then 2, then 1; the process ends at `finished`.
- An `operationId` retry for the same action is idempotent. Reusing it for a different action, or advancing from an invalid state, returns 409. Version-checked updates reject concurrent state changes.
- The retained administrative relative-action API requests `advance` and `previous` each move one stage per request. `previous` moves the persistent stage cursor back one stage without changing any snapshotted question, answer, score, or rank. From question zero, previous enters opening; from a zero-question `podium_preview`, previous also enters opening. Previous from opening returns 409. From `finished`, it returns to the last existing announced rank in the 3rd → 2nd → 1st sequence, or `podium_preview` if there were no winners. Presenter navigation saves absolute positions through the background writer described below; manual progression remains available while those writes are pending.
- The admin console uses one authenticated `GET /api/admin/presentation` for each successful startup check, visible-resume check, and normal state refresh. Its 401 is treated as an unauthenticated session. If a startup or visible-resume state read fails with a non-401 result, the session-only GET is used as a fallback: `authenticated: false` returns to the PIN flow, `authenticated: true` keeps retrying the state read, and a failed fallback preserves prior auth state or leaves initial auth unknown while checked refreshes retry. Normal periodic refreshes for a confirmed session do not issue this fallback. This removes one sequential GET from a successful cold-start refresh; no elapsed-time improvement is claimed without a measured baseline.
- Admin actions `hide` and `show` durably set `projectionHidden`; this can be set before `start`. While hidden, the public API returns only `{ state: 'standby' }`, including while the current stage is opening. Showing restores the current projection stage without changing it. `aggregate` replaces the snapshot without changing visibility or projection hiding. `reset` returns a started or finished session to opening at cursor zero, updates only state/cursor and `version`, and does not change snapshot/revision, ranking, result publication, or projection visibility. Reset is rejected while not started. Before start, `not_started` remains the administrative state and the public screen shows the opening cover design.
- Presentation has one mode: answer explanations are always included in the public projection. The old persisted `presentation_mode` value has no effect, and `setMode` requests are rejected. The question and answer stages remain separate manual stages; ranking stages remain manual in 3rd → 2nd → 1st order. Hiding the projection and moving backward work as before; score/rank snapshots remain fixed until the next explicit aggregate.
- Presentation stages use one plain white 16:9 slide fitted inside a solid-color letterbox. The slide has no persistent header, footer, topline, or bottomline. On answer entry, the ordinal and question appear immediately; all multiple-choice options or the free-text model-answer heading and text remain in the initial DOM and accessibility tree and fade in together after a 100ms delay over 350ms. An existing explanation or published free-text response list fades in after a 350ms delay over 300ms. A stable question-ID key prevents same-question polls and rerenders from replaying the answer reveal; leaving and re-entering an answer stage, including direct answer entry, plays it again. The animation changes opacity only, leaves all content in natural layout, does not delay progression, and does not control publication. Rank entry uses the motion and timing specified in R8-S8. All displayed tied-winner cards, names, scores, answer summaries, and any additional-winner count remain in the initial DOM and accessibility tree and natural layout, then reveal together through one inner content wrapper after the 760ms boundary over 540ms. A stable rank key prevents same-rank polls and rerenders from replaying the reveal; leaving and re-entering a rank stage, including direct rank entry, plays it once again. Reduced motion suppresses rank entrance animations and shows rank content and static decoration immediately. No JavaScript timer or React animation state controls answer or rank entrance. Reveal groups remain in natural layout and do not affect fit measurement. Progression announcements use only the concise live region specified below.
- Every presentation stage renders all of its content at once inside the slide, with no page or stage-content vertical scrolling, clipping, line clamping, or pagination. A shared natural-size content layer is uniformly scaled down as needed to fit the canvas content box, with no minimum scale; viewport, fullscreen, content, image, and font changes trigger refitting. This applies to public and authenticated presenter projections equally. The `it-literacy-005` answer stage continues to show its model answer without participant response rows.
- Presenter navigation is manual and uses absolute position requests through the authenticated admin API and operation IDs. The presenter screen has no start/publication controls, management panel or links, persistent operation footer, or always-visible navigation buttons. The admin page owns start and publication and shows retryable failures, publication state, and current session state. Local navigation remains available while position persistence is pending and during 409 reconciliation: each accepted input updates the in-memory cursor and preloaded projection immediately. A single background writer serializes position POSTs and coalesces intermediate unsent targets into the newest absolute state/index. Ambiguous transport failures retry the exact sent request envelope with its original operation ID unless a newer unsent target supersedes it; never reuse an operation ID with a changed request. A 409 triggers controls/deck reconciliation; when the snapshot revision is unchanged and the latest target exists in that deck, rebase that target on the refreshed session version and retry it with a new operation ID. If the revision changed, discard the old-deck target and adopt the refreshed server cursor. Only server-accepted position writes enter the operation ledger; coalesced unsent targets create no ledger entries. The final slide uses canonical cursor index `max(questionCount - 1, 0)`. Teardown clears pending targets and retry timers and aborts any active request. A position response is validated against the five controls (`state`, nonnegative integer `version`, nonnegative integer `questionIndex` and `questionCount`, and boolean `projectionHidden`); a valid response is authoritative and is applied to the current in-memory deck. A matching normal success causes no operation-triggered session or controls GET and does not re-fetch the deck. Poll responses started before a newer local navigation, and polls overlapping pending position persistence, cannot roll the presenter back. If returned controls do not identify a slide in the loaded deck, controls are not treated as reconciled: progression is disabled while controls and deck are re-synchronized, and no neighboring slide is substituted. A 401 clears private controls and deck. Version alone does not establish that controls and a cached deck belong to the same session. Authorization checks remain unchanged.
- Stage progression is available only to a confirmed presenter whose authenticated deck has loaded successfully, through Space, Enter, ArrowRight, ArrowLeft for previous, and horizontal pointer swipe (left advances, right returns). The existing slide-surface click/tap advance remains pending user confirmation and is retained provisionally. Controls are enabled only while both `presenter=1` and a valid admin session are confirmed; handlers remain inactive until the deck is ready. Repeated keys, modifier keys (Shift, Alt, Ctrl, Meta), and interactive, input, editable, or dialog targets do not trigger progression; repeat, multi-touch, canceled, vertical, and in-flight gestures do not add a separate mutation request because their position merges into the single serialized writer, and a swipe's follow-up click is suppressed. Public `/presentation` spectators are read-only. Movement cannot start a not-started session; finished blocks forward movement but permits previous.
- The viewport projection uses the full viewport without reserving footer height or causing page scroll. The 16:9 slide canvas and safe area remain within that viewport. Presenter progression never requests browser fullscreen. Unsupported or rejected fullscreen, and exiting fullscreen with Escape, leave the viewport projection and manual progression usable; fullscreen is not automatically retried. Admin start, opening the projection tab, polling, idle time, and reload never request fullscreen.

### `GET /api/questions/batch`

- No query parameters or participant session are required.
- Response 200: `{ questions: [{ id, question, choices, answerType }] }`. A valid batch contains exactly the first five dedicated exam questions ordered by `exam_questions.id ASC`; the endpoint selects up to five available rows, and an incomplete result is rejected by the client. `answerType` is `selected` or `freeText` according to the existing fifth-question key rule.
- This public quiz payload excludes answer keys, explanations, scores, and assessment details. The client requires exactly five unique questions with strictly increasing IDs before starting the exam; fewer rows, duplicates, or invalid ordering cannot be used as a partial quiz.
- Response 5xx or a network failure is retryable and does not start the exam.

### `/api/answers/batch`

`POST` creates or revises a five-answer submission; `GET` restores a confirmed submission.

#### `POST`

- Request: `{ submissionId: UUID, operationId: UUID, expectedRevision: integer, answers: [{ questionId, selectedIndex } | { questionId, freeText }] }`
- `answers` must contain exactly five distinct questions in the current fixed exam set for initial submission; revisions must use the same saved question set.
- A correction of a historical choice-shaped fifth answer must replace that value with a valid new `freeText` answer; the legacy selected value is never accepted or resent as the fifth answer.
- Requires same-origin `Origin` and a valid signed participant cookie whose participant still exists. Participant identity is taken only from that cookie.
- Answer APIs currently have no rate limit; failed sign-in attempts are rate-limited only on `POST /api/participants/session`.
- `expectedRevision` is `0` for initial save and the current saved revision for a correction. A successful write advances the revision by one.
- Publication visibility is advisory for answer writes. The UI disables correction while results are visible, but a stale or direct request may still save if ownership, operation ID, and expected revision are valid. Visibility does not acquire a shared serialization row in the answer transaction, and the answer API does not return a publication-lock status.
- On save, the server captures the current question version for every submitted question in `exam_answer_submissions.question_versions`; callers cannot supply or override this map. Historical submissions with absent maps remain unversioned and are not backfilled.
- Initial creation and correction are each one transaction. Corrections update the same submission answer rows and do not append to `exam_answer_logs`.
- `operationId` is unique per deliberate save. Repeating it with the same submission ID and canonical payload returns the original revision; reusing it with a different payload is rejected. Identical requests in one process may be coalesced while the save is in flight, but database operation-ledger uniqueness and replay checks remain the cross-instance idempotency authority. Revision mismatches return 409.
- An exact replay of an already committed operation returns its original success without a write, independent of current visibility. Answer writes are atomic with their operation ledger and use a first-write reservation/CAS path that avoids beginning with a read transaction; they do not serialize with show/hide/re-show transitions. A published result uses the latest explicitly aggregated snapshot, so an answer saved after aggregation can remain absent or stale until the next explicit aggregation.
- After a newly committed free-text answer, assessment starts asynchronously after the response and is scoped to the saved `submissionId` and revision. For a process-local coalesced save, only the initiating request receives the assessment target; joined requests receive replay-shaped results and do not schedule duplicate work. An idempotent operation replay does not start another assessment. Missing JEV configuration leaves the durable pending assessment for the retry worker.
- Response 200: `{ submissionId, revision }`; no correctness, correct index, explanation, score, or pass/fail data is returned.
- Response 400/401/403/404/409: invalid request/question set, missing participant, origin failure, missing submission, or operation/revision conflict.
- Response 503: database serialization remained unavailable after bounded retry; returns `{ error, code: "DATABASE_LOCKED" }` and is a retryable database failure, not a publication lock.
- If a save conflicts because its `expectedRevision` is stale, the client reloads the canonical persisted submission and revision with GET while keeping the local draft separate for user review. It does not resend automatically; a user must explicitly resubmit the reviewed draft against the canonical revision. If GET does not return the same submission ID and a complete, valid answer set, remain on completion with correction disabled.
- Publication visibility is not an answer-save error. The UI disables correction while the last observed state is visible; a stale or direct request can still save, subject to ownership, idempotency, and revision validation.

### `GET /api/answers/latest`

- Requires a valid signed participant cookie whose participant still exists. The participant ID is never accepted from the client. Optional `scope=assisted` resolves the authenticated owner's registered target; unknown scope returns 400 and a missing target returns 404.
- All responses are `Cache-Control: private, no-store` because the payload contains saved participant answers.
- Returns `{ submission: null }` when the participant has no saved submission.
- Returns the participant's latest submission using `updatedAt DESC, revision DESC, createdAt DESC, id DESC`; the payload uses the same answer shape as `GET /api/answers/batch`.
- Returns 401 for a missing or invalid participant session. Database and API failures remain errors and must not be converted to an empty submission.

#### `GET /api/answers/batch?submissionId={UUID}[&scope=assisted]`

- Requires a valid signed participant cookie. By default, a submission is visible only to its owner; with `scope=assisted`, the authenticated owner resolves to their registered target. Missing and non-owned submissions both return 404.
- Response 200: `{ submissionId, revision, answers: [{ questionId, answerKind, selectedIndex, freeText }], resultsVisible: boolean }`. Legacy answers have `answerKind: legacy`; no grading fields are returned. `resultsVisible` reports the current participant-results publication setting so the client can gate correction controls; it contains no result data.
- A legacy fifth answer is identified as its known historical choice-shaped form. It remains unconverted and ungraded during restore; correction requires a newly entered free-text answer.
- Used to restore confirmed answers or reload the canonical saved submission and revision after a conflict; the client preserves any unsaved local draft separately for review.
- Response 400/401/404: invalid submission ID, missing participant session, or unavailable submission.

### `/api/participants/assisted`

- `GET` requires the valid signed participant cookie and an existing participant row. It returns `{ participant: { id, name } | null, hasSubmission: boolean, eligible: boolean }` with `Cache-Control: private, no-store`. `eligible` is true only when the authenticated participant has a completed submission, has no assisted target, and is not another owner's target. An existing target remains available even though `eligible` is false.
- `POST` requires same-origin `Origin` and the valid owner cookie. Request: `{ name: string }`; extra properties, blank names, and names longer than 120 characters are rejected. The name is trimmed and NFC-normalized, must differ from the owner's normalized name, and must not already belong to another participant. A completed owner who is not an assisted target may register exactly one target. Target participant creation and owner-target link insertion are one transaction; database uniqueness protects concurrent creation.
- Repeating registration for the same owner and normalized name returns the existing `{ participant, hasSubmission }` with 200. Registering a different name for an owner who already has a target returns 409. Owner incomplete, owner is itself a target, and name conflicts return 409. Invalid request returns 400, missing/invalid session returns 401, invalid Origin returns 403, excessive name-entry attempts return 429, and unavailable participant authentication configuration returns 503.
- This API never sets or replaces a participant cookie. The owner cookie authorizes `scope=assisted` access to the linked target; the target's regular PIN login resolves to the same participant and submission. Assisted access cannot register another target.
- Name-entry attempts use the shared participant authentication rate limiter. Responses containing participant state use `Cache-Control: private, no-store`.

### Assisted scope on `/api/answers/latest` and `/api/answers/batch`

- `scope=assisted` is accepted by `GET /api/answers/latest`, `GET /api/answers/batch`, and `POST /api/answers/batch`. The server derives the target from the authenticated cookie participant's `assisted_participants` relationship; callers cannot supply a participant ID.
- With no scope, these endpoints continue to address the cookie participant. Unknown scope returns 400 and an owner with no target receives 404 for assisted scope. Missing/invalid cookie returns 401 and answer writes still require a valid same-origin `Origin` (403 otherwise).
- Submission ownership checks, idempotency, revision conflict handling, fixed question validation, and answer response shape remain the same for both scopes. Owner and target submissions are independent.
- The publication lock for an existing submission applies identically to both scopes; first-time submissions remain unaffected.

### `POST /api/internal/jev/retry`

- Requires `Authorization: Bearer <JEV_RETRY_SECRET>`; accepts no answer text from callers.
- Processes up to five due durable assessment jobs with a 45-second lease and compare-and-set claim. Transient failures use bounded exponential backoff. A privileged call with `?retryFailed=1` requeues terminal failures.
- The observed state flow is `pending` → `processing` under a 45-second lease → `graded`; retryable failures return to `pending` with bounded exponential backoff, and permanent failures or the eighth attempt end in `failed`. The provider request timeout is 30 seconds. These implementation values are not service-level objectives.
- Response contains aggregate processed, graded, retried, and failed counts only. Configure an external scheduler to call periodically; there is no scheduler configuration, monitored invocation, or assigned operational owner in this repository.
- JEV grading uses the versioned Q5 question, expected answer, and rubric. The only supported current pair is `tamami-egg-v1` / `jev-q5-keywords30-30-jev40-v1`; missing, unknown, and mismatched versions fail before calling the provider. It uses `TYPESAFE_API_KEY`, optional `TYPESAFE_MODEL` (default `jev-latest`), and optional `TYPESAFE_BASE_URL`. Responses are strictly checked for score and probability keys 0–9, finite score values in 0–9, confidence in 0–1, and probabilities summing to 1. A mismatch between the returned score and probability-weighted score is logged as a diagnostic warning and does not reject an otherwise valid response. The JEV raw score is retained for audit; `normalized_score` stores the complete weighted Q5 total and confidence is ignored. The expected answer and question text are unchanged from `tamami-egg-v1`.

### `/api/participants/session`

- `POST` request: `{ name: string, pin: string }`; PIN must be four ASCII digits, including leading zeroes. The configured `PARTICIPANT_PIN` is validated the same way and compared in constant time.
- On success, reuses or creates the case-sensitive trim+NFC participant and returns `{ participant: { id, name }, expiresAt }` with a signed HttpOnly, SameSite=Lax cookie (`Path=/`, Secure in production; default lifetime 30 days).
- Failed authentication is rate-limited in the shared database to 5 attempts per normalized name per 15 minutes by default, shared across all request sources. `PARTICIPANT_RATE_LIMIT_NAME` configures this limit. Failure records contain HMAC fingerprints only and expired records are opportunistically deleted after 24 hours.
- `GET` returns `{ participant: { id, name } | null }` after cookie signature, expiry, and database checks.
- `DELETE` clears the cookie. Both mutating methods require a same-origin `Origin` header.
- PIN, session secret, or shared database configuration failures fail closed. PINs and secrets are never returned.

### `/api/admin/session`

- `GET` returns `{ authenticated: boolean }` and is always `no-store`.
- The admin console does not need this endpoint on successful startup or state refresh: it confirms authentication through the protected `GET /api/admin/presentation`, which also returns the needed state. On a non-401 failure from the startup or visible-resume state read, the console uses this endpoint as an authentication-only fallback. A 401 from the protected read clears authentication and stops polling until login or a visible-resume recheck; normal periodic refresh failures do not issue a session GET. This endpoint is also used by the presenter page's control gate.
- `POST` requires same-origin `Origin` and `{ pin }`; on success, it sets the separate signed HttpOnly admin cookie and returns `{ authenticated: true }`. Missing admin environment configuration fails closed with 503; invalid PIN returns 401.
- `DELETE` requires same-origin `Origin`, clears only the admin cookie, and returns `{ authenticated: false }`.

### `/api/admin/presentation`

- `GET` requires a valid admin cookie and returns the complete current snapshot: `{ state, version, snapshotRevision, questionIndex, questionCount, projectionHidden, questions: [{ id, question, choices, correctIndex, correctAnswer, explanation, answerType }], entries: [{ displayName, score, rank, answers: [{ questionId, answerKind, selectedIndex, freeText, rawScore, normalizedScore }] }] }`. `answerKind` is `unanswered` for missing answers; legacy answers remain distinct. The presentation session also persists internal `questionVersions` and `rubricVersions` maps; these are not exposed in the response. `?view=controls` returns only `{ state, version, snapshotRevision, questionIndex, questionCount, projectionHidden }` for lightweight presenter synchronization.
- The admin client uses one authenticated GET per successful startup check, visible-resume check, and normal poll. If a startup or visible-resume read fails without a 401, it checks the session endpoint once to distinguish unauthenticated access from retryable state failure; if that check fails, an unknown initial auth state remains unknown and the client retries with a checked refresh. This fallback is not used by periodic refreshes for a confirmed session. The presenter uses `?view=controls` for normal polls and checks the session endpoint only initially and on visible resume. Admin and presenter polls run only while visible and refresh immediately on visible resume; focus alone does not pause them. An admin 401 clears its authenticated state and stops polling; a presenter 401 stops polling and clears controls and its private deck until login or a visible-resume recheck. These client refresh rules do not change either response shape.
- `POST` requires admin cookie, same-origin `Origin`, and `{ operationId, action: 'aggregate' | 'start' | 'advance' | 'previous' | 'position' | 'hide' | 'show' | 'reset' }`. Existing `start`, `advance`, `previous`, `hide`, `show`, `aggregate`, and `reset` actions remain available for their existing admin workflows. Presenter `advance`/`previous` requests may include `expectedSnapshotRevision`, which rejects navigation with 409 if the deck became stale. Absolute `position` requests require `{ state, questionIndex, expectedSnapshotRevision, expectedSessionVersion }`; the nonnegative integer `expectedSessionVersion` must equal the current session version after exact idempotent replay is checked, otherwise the server returns 409 before changing the cursor. Position operation IDs are bound to the target and both expected versions, so a retry of the exact request is idempotent while changing any bound field with the same ID returns 409. The existing SQL version compare-and-swap remains in place. Valid positions are checked against the loaded snapshot and terminal positions use canonical cursor index `max(questionCount - 1, 0)`. Only accepted position requests are recorded in the operation ledger; coalesced unsent client targets do not create entries. On success it returns the confirmed `{ state, version, snapshotRevision, questionIndex, questionCount, projectionHidden }`; presenter clients validate these fields before applying the response. A newly recorded `aggregate` operation also returns `aggregationSummary: { snapshotUpdated, includedSubmissionCount, excludedSubmissionCount, excludedReasonCounts: { questionVersionMismatch, q5AssessmentVersionMismatch } }`; reason counts are non-exclusive and the excluded submission count is unique. If at least one submission is included, `snapshotUpdated` is true and the snapshot is rebuilt atomically, capturing the session's `questionVersions` and `rubricVersions` and incrementing `snapshotRevision`. If none are included because completed version-incompatible submissions were excluded, `snapshotUpdated` is false and the existing snapshot and revision are preserved. With no submissions or only structurally incomplete submissions, the explicit empty aggregation proceeds and `snapshotUpdated` is true, including when there are no participants. Replaying an operation recorded after this summary was introduced returns its stored summary; a replay of a pre-migration aggregate operation may omit `aggregationSummary` because historical counts are not reconstructed. Neither case publishes results or changes projection visibility. `start` requires a nonzero revision whose Q5 question/rubric version maps match the supported pair; an old, missing, or mismatched version snapshot returns 409 and remains unstarted. `start` and publication also require a nonzero revision. `start` and `reset` place a started presentation at `opening`, cursor zero. Replayed operations do not run twice; ID/action conflicts and state/version conflicts return 409. Deprecated `setMode` actions are rejected as invalid requests.
- Both methods are `no-store`; unauthenticated access returns 401. A valid session's mutation with an invalid same-origin `Origin` returns 403. Database/service failures return 503.

### `GET /api/admin/presentation/deck`

- Requires a valid admin cookie and returns `{ snapshotRevision, questionCount, questionIndex, slides }` for the same transactionally read snapshot revision. The deck begins with `opening` at cursor zero, followed by question and answer slides, `podium_preview`, rank announcements, and `finished`; zero-question decks still include opening followed by `podium_preview`. Slides include answer keys, explanations, participant responses, and rank announcements. Every rank slide includes each winner's own `questionResults` as specified in R8. It is `no-store` and is never available through the public presentation API. Missing or invalid admin authentication returns 401; database/service failures return 503.
- The presenter loads this endpoint when authenticated controls show a started presentation, then keeps the returned slides in memory. It reloads only when the controls revision changes; ordinary progression does not fetch or regenerate slide content. A deck from a different revision is discarded and retried on a later poll. A new presenter tab loads the current deck once.

### `GET /api/presentation`

- Returns the server's current public projection and is `no-store`; answer-stage explanations are always included.
- The public spectator client continues polling this endpoint while the document is hidden. Each request reads the projection in one consistent transaction, with access bounded by stage: hidden returns `{ state: 'standby' }` before question, entry, or source-question reads; `question` reads only the cursor-indexed question; `answer` reads the cursor snapshot and needed source-question metadata, plus entries only for non-Q5 free-text responses; rank stages load only detail needed for announced winners; `podium_preview` and `finished` skip question, entry, and source-question reads. Free-text response ordering remains rank then display name. No projection result is cached across users or requests. These access rules do not alter the response shapes below.
- In `question` / `answer`, response is `{ state, question: ... }`. `ordinal` is one-based. The `question` state omits all answer keys and explanation. Multiple-choice answer states include `correctAnswer`, `correctIndex`, and `explanation`; a non-empty snapshot explanation is preserved, while a null or blank legacy snapshot explanation falls back to `exam_questions.explanation` resolved by snapshot `sourceQuestionId`. An answer stage whose source question key is exactly `it-literacy-005` includes `expectedAnswer` and omits the optional `responses` property. Other free-text answer stages include `expectedAnswer` and participant responses with raw similarity and normalized point contribution. The repository looks up source question keys and fallback explanations in one batch using snapshot `sourceQuestionId` values. If a source row is missing or its current key differs from `it-literacy-005`, responses are retained because the fifth-question identity cannot be confirmed. Identity is never inferred from position or `freeText` type. Because snapshots do not store the historical key, a source-key rename or source-ID reuse cannot be recognized as a former fifth question. Confidence, rubric, raw JEV response, and assessment state are omitted.
- In a rank announcement, response is `{ state, winners: [{ displayName, score, rank, questionResults }] }`, containing every tied participant for only the announced rank. Each result has snapshot `position`, `question` (or null if unavailable), and an `answer` state: selected choice value with optional correctness, saved free text, unanswered, legacy, or unavailable. Question text and answer data are joined by answer `questionId` and snapshot `sourceQuestionId`. The free-text `normalizedScore` is included only for a source question confirmed by current key `it-literacy-005`, remains 0–1 as saved, and distinguishes zero from null; when source identity or score validity is uncertain, a neutral `scoreStatus: 'unavailable'` is used and no score is returned. No raw score or assessment internals are returned. `podium_preview` has no `winners` property. Other states return only `{ state }`.
- When the durable projection standby flag is on, the sole response is `{ state: 'standby' }`, independent of the private presentation stage.

### `/api/admin/participant-results`

- `POST` requires a valid admin cookie, same-origin `Origin`, and `{ visible: boolean }`.
- Response 200: `{ visible: boolean }`; responses are `Cache-Control: private, no-store`.
- Results can be hidden regardless of presentation session existence or state. Publication requires a nonzero `snapshot_revision`; publishing an unaggregated session returns 409 and leaves results private. Migration 0012 backfills existing settings history, and migration 0013 preserves valid existing snapshots at revision 1 while marking sessions without snapshots revision 0. Published results are available only to participants with a valid snapshot entry; participants without a snapshot entry or with a malformed snapshot receive `{ state: 'unavailable' }`.
- Visibility operations do not mutate projection visibility, snapshot revision, or presentation version. Scores and rankings change only on a later explicit aggregate. Hiding and repeated already-public requests do not rebuild the snapshot.

### `GET /api/participants/results`

- Requires a valid signed participant cookie whose participant still exists; by default identity comes only from that cookie. Optional `scope=assisted` resolves the authenticated owner's registered target server-side; callers cannot supply a participant ID, and a missing target returns 404.
- The results page may link between default and `scope=assisted` views only for an owner with a submitted target. The assisted view links back to default scope. Links do not grant access: each request revalidates the cookie and owner-target relationship, and visibility is checked independently; while private, both views retain the waiting response.
- Response 200 while private: `{ state: 'waiting' }`. Response 200 when published and the participant has a snapshot entry: `{ state: 'visible', rank, isAggregationTarget, participantCount, score, maxScore, questions }`, where `rank` is null for non-targets, `participantCount` counts only aggregation targets, and `maxScore` is the number of snapshotted questions. Each question is `{ position, question, answer }`, and `answer` is `{ kind: 'selected', value, correctness: 'correct' | 'incorrect' | 'unavailable' }`, `{ kind: 'freeText', value, score: number | null }`, `{ kind: 'unanswered' }`, or `{ kind: 'legacy' }`. The results screen renders the rank as `順位 / 集計対象人数` and the score as `得点 / 最大得点`, with rank and score emphasized over their denominators; the summary cards remain side by side on mobile and the score with its denominator stays on one line. Data comes only from the authenticated participant's shared presentation question and entry snapshots; current question data is not consulted outside the snapshot. A participant without a snapshot entry or with a malformed snapshot receives `{ state: 'unavailable' }` (or the existing unavailable server error). No correct choice, raw answers JSON, raw score, JEV data, internal assessment data, names, or other participants' information is returned. Publication exposes the most recently aggregated snapshot; publication itself does not refresh it. Migration 0012's `ever_published` marker backfills all existing visibility-settings rows true; an exceptional prior false write before initial publication is therefore treated as previously published.
- Invalid or missing sessions return 401. All responses are `Cache-Control: private, no-store`.

### `/api/participants/results/share` and `/api/shared-results/[token]`

- Share management GET resolves the assisted target only from the signed owner cookie and returns `{ exists, issuedAt, expiresAt, expired }`; it never returns a stored token or reconstructs a URL. POST accepts no target ID and returns only `{ path, issuedAt, expiresAt }`, with `path` containing a versioned `v1.<random>.<mac>` base64url token. Its random component remains 32 random bytes (43 base64url characters); the 32-byte HMAC-SHA256 tag is domain-separated and signed with a key derived from `PARTICIPANT_SESSION_SECRET` under a fixed share-token purpose. The client combines that path with its current origin. Reissue atomically replaces the owner row and token hash. POST is permitted only when `getParticipantResult(targetId)` is `visible`; GET and DELETE remain available while results are private. DELETE is idempotent.
- POST and DELETE require same-origin `Origin`. All three management methods require an existing participant session. GET and POST use a namespaced HMAC-fingerprint rate limit (20 requests per owner per 15 minutes); DELETE uses a separate owner namespace with the same limit so reads/reissues cannot consume the stop allowance. Public GET and SSR page reads verify the token MAC, reserve the same namespaced HMAC-fingerprint counter for its full-token hash (60 requests per token per 15 minutes), and only then query for an active share row. Malformed tokens and syntactically valid tokens with an invalid MAC are rejected before DB lookup and do not create counters; signed unknown, expired, revoked, or relationship-mismatched tokens are metered because their MAC proves they were issued by the application. This avoids trusting caller-supplied forwarded headers and prevents one share from consuming another share's or management API's allowance. Rate-limit storage contains no raw IP, token, or URL.
- The token must be exactly `v1.<43-char-random>.<43-char-MAC>` and the HMAC must verify in constant time before rate-limit reservation or DB lookup. The database stores only SHA-256 of the full token, never the plaintext token. A valid unexpired row must still match the current `assisted_participants` relationship before `getParticipantResult(targetId)` is called. Invalid syntax/MAC, unknown/revoked/expired tokens, deleted targets, relationship mismatch, and per-token rate-limit exhaustion all return the same 404. Rotating `PARTICIPANT_SESSION_SECRET` invalidates existing share URLs; owners can issue replacements.
- Public GET accepts no participant ID and does not fall back to participant-cookie authorization. It returns only the existing participant result contract, including `waiting` or `unavailable` when applicable; it does not disclose owner ID or other participants. Both public and management responses are `Cache-Control: private, no-store`, `Referrer-Policy: no-referrer`, and `X-Robots-Tag: noindex, nofollow, noarchive`.
- `/shared-results/[token]` is dynamic, uses the same server-side share validation for its first render, and has generic noindex metadata. Its client refresh uses only the share API with `credentials: 'omit'`; a confirmed waiting/404 state clears previously displayed result data. Each refresh supersedes and aborts the prior request, and only the latest request generation may update the page, so a delayed visible response cannot restore details after a newer waiting/404 result. The page offers no answer editing, participant-result link, or share-management action. Both result surfaces use the pure `ParticipantResultDetails` renderer.

| Guest                 | No participant cookie                                                                          | Read public question prompts and public presentation projection; attempt participant sign-in                                       | Cannot submit or read participant answers, admin deck, or participant results                                                                      |
| Participant           | Valid signed participant cookie plus an existing participant row                               | Own submission, correction, and own published result; same-origin answer mutations                                                 | Client-supplied participant IDs are ignored/rejected; cookie expiry, invalid signature, missing participant, PIN/secret rotation invalidate access |
| Proxy owner           | The authenticated participant relationship in `assisted_participants`                          | Resolve one linked target through server-side `scope=assisted`; create a target only after owner completion and eligibility checks | Cannot choose an arbitrary target ID, replace owner cookie, register a second/different target, or create a target when themselves a target        |
| Assisted target       | Its own participant identity when signing in normally; owner relationship only for proxy scope | Has a separate participant record and submission; owner can operate its linked target through the server-resolved relationship     | Target does not inherit owner identity and cannot create another assisted target                                                                   |
| Administrator         | Separate admin PIN and signed `stcirt_admin_presentation` cookie                               | Read private presentation/deck; mutate presentation and result visibility with a valid same-origin Origin                          | Participant cookie never grants admin; `presenter=1` is not authorization; invalid/missing configuration fails closed                              |
| Internal retry caller | `Authorization: Bearer <JEV_RETRY_SECRET>`                                                     | Process due durable assessment jobs; request body cannot supply answer content                                                     | No participant or admin authority; `retryFailed=1` is restricted to this secret-protected endpoint                                                 |

Participant failed sign-in and assisted-name registration share the database-backed per-normalized-name limiter (default five attempts per 15 minutes). It stores HMAC fingerprints, not names or IP addresses. Answer endpoints themselves have no rate limit. Mutating participant/admin endpoints validate same-origin `Origin`; protected reads rely on the appropriate signed cookie. Existing cookies expire, and rotating the participant PIN/secret or admin secret invalidates its corresponding session.

Shared-result management and public reads use separate HMAC-fingerprinted rate-limit namespaces. The bearer URL is transferable and therefore grants access to anyone who obtains it; it does not prove the viewer is the intended assisted target. Application responses and error handling do not log tokens or complete share URLs.

JEV grading uses server-only `TYPESAFE_API_KEY`, optional `TYPESAFE_MODEL` (default `jev-latest`), and optional `TYPESAFE_BASE_URL`. Newly saved free-text answers trigger one asynchronous assessment attempt after the answer response. The durable retry worker requires `JEV_RETRY_SECRET`; configure an external deployment scheduler to call `POST /api/internal/jev/retry` periodically for pending jobs, including jobs left pending when JEV configuration or post-response execution is unavailable. The repository has no scheduler configuration. An authenticated `?retryFailed=1` call requeues terminal failures.

Runtime configuration requires `TURSO_DATABASE_URL`, `TURSO_AUTH_TOKEN`, `PARTICIPANT_PIN`, and `PARTICIPANT_SESSION_SECRET` for participant authentication. `PARTICIPANT_PIN` is exactly four ASCII digits, including possible leading zeroes. The secret must have at least 32 bytes. The cookie payload is `{ id, exp }`; its HMAC-SHA256 signing key is derived as `HMAC-SHA256(PARTICIPANT_SESSION_SECRET, "stcirt-participant-session-v1" + NUL + PARTICIPANT_PIN)`. The `stcirt-participant-session-v1` purpose label and NUL delimiter are fixed. PIN or secret changes invalidate existing cookies. Rate-limit HMAC key derivation uses a separate fixed purpose label and does not include the PIN, so PIN rotation does not reset rate limits. Old cookies are rejected and participants must sign in again. `PARTICIPANT_PIN_HASH`, `PARTICIPANT_PIN_PEPPER`, and `PARTICIPANT_EVENT_VERSION` are retired.

Admin presentation authentication separately requires `ADMIN_PRESENTATION_PIN` and `ADMIN_PRESENTATION_SESSION_SECRET`; the PIN must be nonempty and at most 128 characters, and the secret must have at least 32 bytes. Missing configuration fails closed. The admin cookie is `stcirt_admin_presentation`, HttpOnly, SameSite=Strict, Secure in production, and expires after eight hours. Its HMAC-SHA256 key is derived from the admin secret and fixed `stcirt-admin-presentation-session-v1` purpose label. Admin secrets/cookies are not shared with participant authentication.

Use `pnpm participant-auth generate` to create the participant pair in `.env.local`. It prompts twice for a user-selected four-digit ASCII PIN using hidden terminal input, preserving leading zeroes, and generates the session secret automatically. Non-interactive runs fail. It preserves other settings, refuses to overwrite either selected profile key, and writes atomically with mode 0600. Use `--rotate` only for intentional replacement. The default profile is `participant`; use `--profile admin` to create the separate `ADMIN_PRESENTATION_PIN` and `ADMIN_PRESENTATION_SESSION_SECRET` pair. Admin PIN input is hidden and accepts 1–128 characters; its session secret is generated automatically from 32 random bytes and encoded as base64url.

To also sync the newly saved pair to Production in the same command, link the repository to the intended Vercel project, authenticate with Vercel CLI, and run `pnpm participant-auth generate --sync-production` (or add `--profile admin` for admin credentials). This sync does not start a deployment; start a new deployment separately for the changes to take effect. If sync fails, `.env.local` retains the generated pair and the command exits nonzero with instructions to rerun the matching profile's `pnpm participant-auth sync --target production` command. Alternatively, sync a saved pair with `pnpm participant-auth sync --target production` or `--target preview`, adding `--profile admin` when syncing admin values. Sync requires Vercel CLI authentication, upserts only the selected profile's two values through stdin using `--force --sensitive`, never deploys, and exits nonzero if either upsert fails. Preview applies to all branches; inspect branch-specific overrides in Vercel separately. Development is excluded because Vercel sensitive variables are supported only for Production and Preview. The Vercel CLI dependency is pinned to version `58.4.4`.

Optional `PARTICIPANT_SESSION_DAYS` accepts 1–90 (default 30); `PARTICIPANT_RATE_LIMIT_NAME` defaults to 5 failed attempts per normalized name per 15 minutes. Question generation and question-management endpoints are not part of the application.
